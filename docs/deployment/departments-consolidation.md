# حذف مفهوم تیم و انتقال به دپارتمان — استقرار کنترل‌شده

این تغییر **فقط حذف منو نیست**. مدل عملیاتی، API، انتخاب‌گرها، اتصال جدول‌های دارایی و تنظیمات اتوماسیون بله از دپارتمان استفاده می‌کنند. جدول‌های قدیمی تیم برای بازیابی نگه داشته می‌شوند ولی دیگر منبع دسترسی یا قابل مدیریت از API نیستند.

## خطای parent_id

- `parentId` باید شناسهٔ واقعی دپارتمان موجود باشد؛ `null` یعنی بدون والد.
- والد ناموجود، خود دپارتمان و والدِ زیرمجموعه با پاسخ **422** رد می‌شوند، نه خطای FK دیتابیس.
- ویرایش درخت زیر قفل رکورد ساختار دوباره بررسی می‌شود؛ فیلدهای ارسال‌نشده دست‌نخورده می‌مانند.
- ذخیرهٔ دپارتمان مستقیم و منتظر نتیجهٔ API است؛ دادهٔ نمونه/کش مرورگر و همگام‌سازی عمومی دیگر دپارتمان نمی‌سازند یا تغییر نمی‌دهند. پاسخ خالی سرور واقعاً فهرست خالی است. فرم در خطا باز می‌ماند.

## سیاست انتقال

1. برای **هر تیم ذخیره‌شده** یک دپارتمان مستقل ساخته می‌شود؛ `legacy_team_id` یکتا نگاشت را نگه می‌دارد. حتی نام‌های یکسان ادغام نمی‌شوند.
2. والد، دپارتمان قبلی تیم است؛ بدون دپارتمان قبلی، ریشه خواهد بود. `active` فعال و وضعیت‌های دیگر غیرفعال می‌شوند. مدیر و شرح حفظ می‌شوند. عضویت از نام یا سمت مدیر حدس زده نمی‌شود.
3. `team_user` به `department_user` با نقش و تاریخ عضویت منتقل می‌شود. هر کاربر می‌تواند عضو چند دپارتمان باشد. عضویت اصلی موجود در `users.department_id` نیز مستقل معتبر است؛ به عضویت اضافیِ تکراری تبدیل نمی‌شود.
4. اتصال‌های `dam_data_table_team` به `dam_data_table_department` منتقل می‌شوند. **هیچ وراثت عضویت/دسترسی از والد وجود ندارد.** مجوزهای قبلی جدول نیز همچنان لازم‌اند؛ محدودیت عضویت، حتی برای مدیر جدول، از بین نمی‌رود. حذف دپارتمان متصل به جدول تا تعیین تکلیف اتصال ممنوع است.
5. ارجاع‌های ساختاری در payload محتوا، ایده/جلسه/دبیرخانه، رکوردهای دامنه و تنظیمات تبدیل می‌شوند: `teamId`، `teamIds`، `toTeamId`، اشتراک‌گذاری `targetType=team`، `permissionLevel=team` و کلیدهای متناظر snake_case. اگر محتوا دپارتمان اصلی متفاوتی دارد، آن حفظ و رابطهٔ اضافی در `departmentIds` نگه‌داری می‌شود. این تبدیل جایگزین بازطراحی ACL محتوا نیست.
6. اتوماسیون بله `department_id` می‌گیرد؛ revision هنگام تغییر بالا می‌رود. پیش‌نویس‌های موقت بات حذف و همهٔ پیام‌های خروجیِ pending لغو می‌شوند تا اطلاعات/شناسهٔ قدیمی دوباره تفسیر نشود. پیام‌های ارسال‌شده و رکوردهای نهایی حذف نمی‌شوند. کاربر پس از استقرار `/start` بفرستد و فرم باز را دوباره آغاز کند.
7. مجوزهای نقش `teams.view/create/edit/delete` به `departments.view/create/edit/delete` منتقل می‌شوند؛ `teams.edit` همچنین `departments.manage_members` می‌گیرد. مجوزهای قدیمی از کاتالوگ نقش حذف می‌شوند؛ این انتقال برای نقش‌های دارای همان مجوز است، نه همهٔ کاربران. **دامنهٔ مجوز مدیریتی دپارتمان سراسری است**؛ مدیر استقرار باید نقش‌های دارای مجوز قدیمی تیم را پیش از اجرا بازبینی کند. محدودیت خواندن جدول همچنان عضویت صریح می‌خواهد.
8. API قدیمی `/teams` و `/bale/asset-tables/{id}/teams` حذف شده‌اند. کلیدهای قدیمی تیم در درخواست نوشتن با 422 رد می‌شوند؛ شناسهٔ تیم هرگز به‌عنوان شناسهٔ دپارتمان پذیرفته نمی‌شود.
9. عضویت/مدیر فقط با `departments.manage_members` تغییر می‌کند؛ ویرایش نام/شرح به تنهایی این مجوز را نمی‌دهد. انتساب دپارتمان اصلی از مدیریت کاربران، علاوه بر مجوز کاربر، مجوز مدیریت اعضا می‌خواهد. ثبت‌نام عمومی نمی‌تواند عضویت مطالبه کند. انتخاب دپارتمان کاربر با **ID** است؛ نام تکراری حدس زده نمی‌شود.

دادهٔ ذخیره‌شدهٔ سرور مرجع است. داده‌های صرفاً مرورگریِ تیم یا فیلدهایی که نسخهٔ قبلی واقعاً در دیتابیس ذخیره نمی‌کرد، قابل بازیابی با این انتقال نیستند. داده‌های تاریخی تیم/عضویت/اتصال قدیمی حذف نمی‌شوند؛ رنگ و نوع قدیمی نیز در همان آرشیو باقی می‌مانند. تاریخچهٔ متنی و کلیدهای قدیمی نقش مثل `team_member` شناسهٔ تاریخی‌اند و عمداً بازنویسی نمی‌شوند.

## نصب بدون SSH و Cron

**اجرای زنده هنوز انجام نشده است. قبل از تولید، روی کپی دیتابیس واقعی تمرین کنید.**

1. از کل دیتابیس، فایل‌های برنامه، `.env` و فضای خصوصی فایل‌ها نسخهٔ پشتیبان قابل بازیابی بگیرید. `APP_KEY` را تغییر ندهید. `.env` هاست را با بستهٔ انتشار جایگزین نکنید.
2. با کنترل‌پنل هاست، دسترسی عمومی نسخهٔ قدیمی و پردازش بله را موقتاً متوقف کنید. فایل PHP عمومی برای اجرای migrate یا SQL نسازید. این طرح worker، Cron یا shell لازم ندارد.
3. پیش‌نیاز نسخهٔ بلهٔ قبلی (`bale-phase1` و `bale-operations`) باید نصب باشد. وجود `teams`, `team_user`, `departments`, `users`, `dam_data_tables`, `dam_data_table_team`, `contents`, `workspace_records`, `domain_records`, `system_settings`, `permissions`, `permission_role`, `activity_logs`, `bale_conversations`, `bale_outbox` را بررسی کنید. راهنمای قبلی `bale-experience.md`/SQLهای بله همچنان پیش‌نیاز است.
4. دیتابیس صحیح را در phpMyAdmin انتخاب و `departments-consolidation.mysql.sql` را اجرا کنید. به `ALTER`, `CREATE` و foreign keyهای InnoDB نیاز است. SQL فقط ساختار را ایجاد می‌کند؛ DDL ممکن است auto-commit شود. وجود جدول به‌تنهایی صحت ستون‌های یک نصب دست‌کاری‌شده را تضمین نمی‌کند؛ `SHOW CREATE TABLE` را بررسی کنید. `FOREIGN_KEY_CHECKS=0` نکنید.
5. بک‌اند جدید و **تمام `frontend/dist/`** را هماهنگ بارگذاری کنید؛ cache نسخهٔ قدیمی PHP/OPcache/CDN را طبق امکان کنترل‌پنل پاک کنید. اگر route/config cache از انتشار قبلی در `backend/bootstrap/cache/` وجود دارد، فایل‌های تولیدشدهٔ `routes*.php` و `config.php` را با File Manager حذف کنید؛ `bootstrap/app.php`، `.env` و فایل‌های خصوصی را حذف نکنید. کد قدیمی نباید همزمان بنویسد. مسیر عمومی وب فقط document root استاندارد Laravel باشد، نه کل backend.
6. دسترسی را برای مدیر فعال باز کنید و در **دپارتمان‌ها → تکمیل انتقال ساختار قبلی**، «اجرای بسته بعدی انتقال» را تا مرحلهٔ `done` بزنید. هر درخواست حداکثر ۵۰ رکورد مبنا را پردازش می‌کند؛ تعداد عضویت‌ها/اتصال‌های هر تیم ممکن است بیشتر باشد. بسته transaction مستقل دارد، checkpoint و نگاشت یکتا هستند. قطع درخواست/تکرار کلیک باعث ساخت دپارتمان‌های تکراری نمی‌شود. چند مدیر نباید همزمان استقرار انجام دهند؛ درخواست‌ها زیر قفل checkpoint سری می‌شوند. محدودیت API ۳۰ درخواست در دقیقه است.
7. تا تکمیل، مسیرهای دادهٔ وابسته با 503 بسته‌اند؛ ورود/خروج، اطلاعات پایهٔ حساب/نقش‌ها و مسیر انتقال برای راه‌اندازی باز هستند. endpoint انتقال فقط مدیر فعال است: `GET/POST /api/v1/departments/consolidation`، بدنهٔ POST: `{ "confirm": true }`؛ از نشست احرازشدهٔ عادی استفاده می‌کند، نه کلید عمومی استقرار. نام مرحله و آخرین ID نمایش داده می‌شود، نه دادهٔ خصوصی.
8. اگر ارجاع به تیم ناموجود یا JSON خراب پیدا شد، بسته متوقف و checkpoint قبلی حفظ می‌شود. **وضعیت را دستی done نکنید** و شناسه‌ها را با نام یا شمارهٔ ظاهراً یکسان جایگزین نکنید. روی نسخهٔ پشتیبان رکورد معیوب را پیدا کرده و مقصد را با مسئول داده تعیین کنید؛ سپس اصلاح کنترل‌شده و ادامهٔ همان بسته. پیام اعتبارسنجی شناسهٔ قدیمی را نشان می‌دهد.
9. بعد از `done` صفحه را کاملاً بارگذاری مجدد کنید؛ نقش‌ها/فرم‌ها/داده‌ها تازه شوند. محدودیت‌ها را با دو عضو از دپارتمان‌های متفاوت و یک عضو صرفاً والد آزمایش کنید. سپس دسترسی عمومی و بله را باز کنید. پیام‌های pending لغوشده خودکار دوباره ارسال نمی‌شوند؛ در صورت لزوم اعلان/یادآوری را از مسیر مجاز دوباره ایجاد کنید.

اگر PHP در اندازهٔ واقعی یک بسته timeout می‌شود، توقف کنید و limit بسته/ظرفیت هاست را روی کپی داده بررسی کنید؛ ارسال پشت‌سرهم کورکورانه توصیه نمی‌شود. هیچ تماس بیرونی برای خود انتقال لازم نیست؛ نیازهای HTTPS و outbound بله همان راهنمای قبلی است.

### کنترل پس از انتقال در phpMyAdmin

```sql
SELECT t.id AS unmapped_team FROM teams t
LEFT JOIN departments d ON d.legacy_team_id = t.id WHERE d.id IS NULL;
SELECT tu.team_id, tu.user_id AS missing_member FROM team_user tu
JOIN departments d ON d.legacy_team_id = tu.team_id
LEFT JOIN department_user du ON du.department_id = d.id AND du.user_id = tu.user_id
WHERE du.user_id IS NULL;
SELECT dt.team_id, dt.dam_data_table_id AS missing_binding FROM dam_data_table_team dt
JOIN departments d ON d.legacy_team_id = dt.team_id
LEFT JOIN dam_data_table_department dd ON dd.department_id = d.id AND dd.dam_data_table_id = dt.dam_data_table_id
WHERE dd.department_id IS NULL;
SELECT `value` FROM system_settings WHERE `key` = 'department_consolidation_private';
```

سه query اول بلافاصله پس از انتقال باید خالی و phase باید done باشد. پس از تغییرات مجاز بعدیِ اعضا/اتصال‌ها، اختلاف با آرشیو طبیعی است. دادهٔ خصوصی بله یا token را برای بررسی خروجی نگیرید.

### برگشت

این انتقال forward-only است؛ `down()` عمداً متوقف می‌شود. در صورت نیاز **دیتابیس و فایل‌های نسخهٔ قبل را با هم از نسخهٔ پشتیبان برگردانید**. برگشت فقط کد، حذف pivot جدید، یا همزمان نگه داشتن نسخهٔ قدیمی مجاز نیست. جدول‌های قدیمی برای بازیابی/ممیزی مانده‌اند، نه برای اجرای نسخهٔ قدیمی پس از تغییرات جدید.

## UI و محدودهٔ امنیت

- منوی مستقل تیم، ساخت/ویرایش تیم، تب تیم و جستجوی تیم حذف شده‌اند؛ انتخاب‌گرهای ایده، ارجاع، پوشه/اشتراک، تحلیل بارکاری و بله از دپارتمان استفاده می‌کنند.
- چهار کارت آماری بالای صفحهٔ قبلی حذف شده‌اند. صفحه مستقیماً فهرست دپارتمان‌ها را نشان می‌دهد.
- فقط دکمهٔ خروج **سایدبار اصلی** حذف شده است؛ خروج حساب در مسیرهای دیگر باقی است.
- این تغییر همهٔ ایرادهای ممیزی قبلی را برطرف نمی‌کند. ACL محتوا/انتشار، دامنهٔ فعالیت‌ها، مالکیت رأی و مسائل چتِ گزارش‌شده در `docs/security/access-control-phase1.md` همچنان نیازمند مرحلهٔ بعدی‌اند؛ نگه‌داری ارجاع‌های عضویت به معنی تأیید امنیت همهٔ آن ماژول‌ها نیست.

## شواهد آزمون

نتیجهٔ نهایی آزمون‌ها و محدودیت محیط در انتهای این سند ثبت می‌شود. آزمون SQLite جایگزین اجرای SQL روی MySQL/MariaDB واقعی، آزمون همزمانی چندپردازه یا تست بلهٔ زنده نیست.

### نتیجهٔ بررسی محلی — 2026-09-28

- کل مجموعهٔ بک‌اند: **200 آزمون / 961 assertion، موفق**؛ PHP 8.5.10 WASM و PHPUnit 12.5.35 روی SQLite حافظه‌ای. شامل ۱۸ سناریوی جدید دپارتمان/انتقال و آزمون بی‌اثر بودن callback قدیمی تیم است. مجموعه‌های قبلی بله نیز با قرارداد دپارتمان اجرا شدند.
- برای اجرای WASM، `mockConsoleOutput=false` موقتاً روی TestCase اعمال و سپس دقیقاً به نسخهٔ اصلی برگردانده شد؛ APP_KEY مصنوعی مخصوص اجرای آزمون از محیط فرایند تأمین شد، نه `.env` تولید.
- TypeScript `tsc --noEmit`: موفق. تست‌های Node: **16 موفق** (چهار تست جدید شامل منطق انتخاب والد و بررسی‌های ساختاری سورس برای ذخیرهٔ API-first/حذف wrapper و خروج سایدبار؛ این‌ها تست مرورگر نیستند).
- Laravel Pint: **28 فایل PHP موفق**؛ `git diff --check` موفق.
- Vite production: **2687 ماژول**؛ خروجی قابل تحویل `frontend/dist/index.html`، `assets/index-XbSUHsQZ.js` و `assets/index-D5xjaxvb.css`. API origin تولید در build تنظیم شده، source map تولید نشده و dist از Git ignore نشده است. هشدار قدیمی اندازهٔ chunk بیش از 500KB همچنان برقرار است.
- SQL MySQL/MariaDB، دیتابیس تولید، مرورگر تعاملی، چندپردازه/همزمانی واقعی، بلهٔ زنده و نصب روی هاست در این محیط آزمایش نشده‌اند. هیچ انتقالی روی دیتابیس واقعی یا استقرار روی هاست انجام نشده است. نتایج بالا رفع موارد باز ممیزی امنیتِ قبلی را ادعا نمی‌کنند.
