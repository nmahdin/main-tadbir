# دریافت مستقیم بله روی هاست بدون Cron/SSH

## تغییر این نسخه

پیام خصوصی یا callback دکمه، از طریق HTTPS POST بله وارد سایت می‌شود؛ همان منوها، اتصال حساب، مجوزها و عملیات قبلی اجرا و پاسخ از `sendMessage` فرستاده می‌شود. پنل لازم نیست باز باشد و دکمهٔ پردازش لازم نیست. Webhook در این مرحله **اختیاری و نیازمند فعال‌سازی صریح مدیر** است.

- migration جدید یا نصب Composer package لازم نیست. جداول هر دو مرحلهٔ قبلی (از جمله SQL عملیات) باید از قبل نصب شده باشند.
- `UpdateProcessor` بین polling و Webhook مشترک است؛ عملیات دامنه، Inbox و Outbox یک تراکنش دارند. ثبت تکراری `update_id` عملیات را دوباره اجرا نمی‌کند. Webhook با offset پیام کم‌شماره‌ترِ خارج از ترتیب را حذف نمی‌کند؛ ترتیب رسیدن هم‌زمان تضمین نشده و فرم نامعتبر باید دوباره شروع شود.
- callback acknowledgment و پاسخ پس از commit هستند. قفل مشغول یا خطای پردازش → 503، نه تأیید کاذب دریافت. به retry دائمی بله تکیه نشده؛ پنل/هاست و پیام واقعی باید آزمایش شوند.
- پاسخ همین پیام پیش از صف اعلان‌های دیگر تلاش می‌شود؛ بودجه نرم ۱۵ ثانیه. 429/pending در پیام بعد یا «ارسال صف» قابل پیگیری است؛ unknown خودکار تکرار نمی‌شود. تضمین exactly-once شبکه یا پاسخ همیشگی آنی نداریم.
- payload باید JSON، حداکثر ۶۴KB و دارای update_id عددی نامنفی و یک نوع آپدیت باشد؛ حد اپلیکیشن درخواست مسیر ۱۲۰ در دقیقه برای هر IP است (سقف رسمی بله نیست). محدودیت بدنه را در وب‌سرور/WAF نیز اعمال کنید؛ middlewareهای PHP ممکن است پیش از کنترلر بدنه را بخوانند.

## مدل امنیتی و پیش‌شرط اجباری استقرار

مستندات رسمی `setWebhook` فقط `url` را معرفی می‌کند؛ هدر `secret_token` یا امضای تلگرام فرض نشده است. این پیاده‌سازی **URL capability / bearer credential** دارد، نه امضای قابل اثبات از مبدأ بله:

- پسوند تصادفی ۲۵۶بیتی (`random_bytes(32)`) مستقل از توکن بات، رمزگذاری با APP_KEY و مقایسهٔ ثابت‌زمان. فقط مسیر دارای credential در حالت Webhook و برای بات فعال/آزمایش‌شده پذیرفته می‌شود.
- آدرس کامل در API تنظیمات، UI، ActivityLog یا پیام خطا نمایش داده نمی‌شود. درخواست‌های HTTP بله از کلاینت بدون event logger عبور می‌کنند. بدنهٔ آپدیت/کد اتصال در Inbox ذخیره نمی‌شود.
- **هر دارندهٔ آدرس کامل می‌تواند آپدیت جعلی بفرستد و شناسهٔ بلهٔ کاربر متصل را جعل کند.** مجوزهای داخلی همچنان بررسی می‌شوند، ولی افشای capability اعتماد به هویت ورودی را از بین می‌برد. آن را دقیقاً مانند رمز عبور نگهداری کنید.
- پیش از فعال‌سازی، از پنل/پشتیبانی هاست بخواهید **کل URI مسیر `/api/v1/bot/bale/webhook/*` را از access/error log، CDN/WAF، APM، request tracing، بک‌آپ عمومی و ابزارهای analytics حذف یا پسوند را ماسک کند**. در نصب زیرمسیر، prefix را متناسب کنید. APP_DEBUG=false و HTTPS معتبر لازم است. برنامه نمی‌تواند لاگ مستقل وب‌سرور را خاموش کند.
- اگر امکان محافظت از این credential وجود ندارد، Webhook را فعال نکنید؛ از دریافت دستی یا واسط احرازاصالت مناسب استفاده کنید. چک‌باکس/تأیید UI ادعای تأیید خودکار امنیت زیرساخت نیست؛ ثبت نیازمند `acknowledge_secret_url=true` مدیر است.
- در افشا، مدیر «تعویض آدرس محرمانه» را بزند؛ URL قدیمی فوراً باطل می‌شود. توکن بات در URL ورودی استفاده نمی‌شود. تعویض با تأیید، ممکن است درخواست‌های در راه به آدرس قدیمی را از دسترس خارج کند؛ در خطا «ثبت مجدد» را اجرا کنید.

## نصب و راه‌اندازی

1. از فایل‌ها/DB backup بگیرید. بک‌اند و فرانت‌اند جدید را با روش فعلی File Manager/FTP منتشر کنید؛ `.env`، APP_KEY و storage فعلی را حفظ کنید. route/config cache قدیمی را طبق روش استقرار پروژه پاک/بازسازی کنید. این مرحله SQL تازه ندارد.
2. مسیر عمومی باید به `backend/public` و فایل‌های Laravel صحیح برسد؛ HTTP Basic Auth، challenge مرورگر، redirect به ورود، یا مسدودسازی عمومی WAF روی مسیر بله نباشد. CORS برای درخواست سرور بله مطرح نیست؛ CSRF کل سایت را خاموش نکنید. route در API و بیرون از auth:sanctum است ولی credential خودش را بررسی می‌کند.
3. `BALE_PUBLIC_BASE_URL` را به آدرس HTTPS عمومی **بک‌اند** (یا APP_URL صحیح) تنظیم کنید؛ مانند `https://api-tadbir.morvarid-daron.ir`. `/api/v1` اضافه نکنید. زیرمسیر نصب پشتیبانی می‌شود. پورت ثبت فقط 443 یا 88؛ آدرس از Host مرورگر ساخته نمی‌شود.
4. پیش‌شرط محرمانگی لاگ بالا را رعایت کنید. PHP/افزونه‌ها/اتصال خروجی به `tapi.bale.ai`/قفل database cache همان پیش‌نیازهای قبلی‌اند. `CACHE_STORE=array` برای تولید مناسب نیست.
5. تنظیمات ← اعلان‌ها ← ربات بله: توکن را ذخیره، بات را فعال و «تست واقعی بات» را اجرا کنید.
6. **«فعال‌سازی دریافت خودکار / ثبت مجدد»** را بزنید و تأیید کنید. مقصد Webhook قبلی جایگزین می‌شود؛ لازم نیست قبلش حذف کنید. برنامه `setWebhook` و سپس بررسی `getWebhookInfo` انجام می‌دهد. وضعیت باید «ثبت‌شده و منطبق» باشد.
7. در گفت‌وگوی خصوصی بات `/start` ارسال کنید. **پردازش یک نوبت را نزنید.** بات نامتصل باید راهنمای اتصال بدهد. در پنل «به‌روزرسانی وضعیت» را بزنید: آخرین Webhook/آخرین دریافت/شناسهٔ آپدیت/مسیر webhook باید به‌روز شوند. این آزمون از ثبت مقصد جداست.
8. در پروفایل کد اتصال بگیرید و به بات بفرستید؛ سپس منوی وظایف یا فرم دارایی را آزمایش کنید. تشخیص فرستنده، اتصال و کنترل مجوز در backend باقی است.

خروجی `frontend/dist` با همان دامنه‌های API/Sanctum فعلی مخزن ساخته می‌شود. برای محیط دیگر build متناسب بسازید. استقرار خودکار روی هاست انجام نشده است.

## اگر پاسخ نرسید

| وضعیت | بررسی |
|---|---|
| ثبت‌شده و منطبق، ولی آخرین Webhook خالی | رسیدن HTTPS به PHP، WAF/challenge، DNS/TLS و نسخهٔ واقعی route را بررسی کنید. موفقیت setWebhook به معنی اجرای handler نیست. لاگ URI محرمانه نگیرید. |
| mismatch یا unconfirmed | تست واقعی و سپس ثبت مجدد؛ در timeout ممکن است بله مقصد را قبلاً ثبت کرده باشد. retry معمولی همان secret را حفظ می‌کند؛ بی‌دلیل rotate نکنید. |
| آخرین دریافت به‌روز، بدون پاسخ | وضعیت Outbox و آخرین ارسال را ببینید. حساب غیرفعال، پیام غیرخصوصی/نوع پشتیبانی‌نشده یا خطای شبکه هم ممکن است پاسخ نداشته باشد. |
| 503 / webhook_processing_failed | قفل/runtime/DB را بررسی کنید؛ خطای خام یا body/URL را در لاگ نریزید. ارسال دوباره همان update اثر ثبت‌شده را تکرار نمی‌کند. |
| webhook_conflict هنگام پردازش دستی | در حالت Webhook انتظار می‌رود getUpdates اجرا نشود؛ دکمهٔ پردازش در UI غیرفعال است. زمان‌بند خارجی قدیمیِ getUpdates را هم متوقف کنید. |
| URL پایه هنوز503 می‌دهد | طبیعی است. آدرس بدون capability نباید قابل دریافت باشد. فقط از دکمهٔ فعال‌سازی استفاده کنید. |

## بازگشت

«حذف Webhook و بازگشت به دریافت دستی» بعد از پاسخ دقیق true بله، secret محلی را باطل می‌کند. اگر حذف ناموفق بود حالت خودکار را دروغین خاموش اعلام نمی‌کنیم. بعد از موفقیت، دریافت فقط با پردازش یک نوبت یا زمان‌بند بیرونی انجام می‌شود. حذف اتصال ربات نیز credential قبلی را با حذف تنظیمات باطل می‌کند.

## بررسی مرجع و آزمون

- مخزن معرفی‌شده: https://github.com/alirezarazavi/larabale — README صریحاً early development/not production ready می‌گوید؛ composer.json برای PHP ^7.2 و Illuminate 5/6 است. `src/LaraBale.php` متد setWebhook دارد، ولی receiver یا احراز مبدأ برای سامانهٔ ما ارائه نمی‌کند. آن بسته نصب و کدش کپی نشده؛ الگوی رسمی HTTP در معماری فعلی استفاده شده است.
- مستندات بررسی‌شده: https://docs.bale.ai/#setwebhook ، https://docs.bale.ai/#getwebhookinfo ، https://docs.bale.ai/#update ، https://docs.bale.ai/#sendmessage . فقط پارامتر مستند `url` به setWebhook ارسال می‌شود.
- تست‌ها API بله را fake می‌کنند. فعال‌سازی/عدم افشای credential، /start مستقیم، اتصال و ثبت گزارش، replay، ترتیب متفاوت، درخواست جعلی، اندازه/JSON، قفل، rollback، timeout، تعویض secret و بازگشت دستی پوشش داده شده‌اند. نتیجهٔ اجرای نهایی در PR ثبت می‌شود.
- هنوز روی هاست واقعی، MySQL هم‌زمان چندفرایندی یا مرورگر کاربر آزمایش نشده است؛ هیچ توکن واقعی استفاده و هیچ Webhook واقعی از این محیط تغییر داده نشده است.
