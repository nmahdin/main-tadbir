# اجرای مرحلهٔ اول اصلاح دسترسی‌ها

تاریخ: ۲۰۲۶-۰۹-۲۸ — شاخه: `arena/01a0e7dd-main-tadbir`

این سند **اجرای بخشی از ممیزی** است، نه اعلام پایان اصلاح مجوزهای همهٔ ماژول‌ها. گزارش اولیه و inventoryها در `access-control-review.md` تصویری از وضعیت قبل از این مرحله هستند.

## تغییرات اجراشده

### حساب، نشست و منبع نقش

- middleware مشترک پس از Sanctum، وضعیت ذخیره‌شدهٔ حساب را در هر درخواست دوباره می‌خواند. حساب blocked/inactive/pending حتی با نشست یا توکن قبلی اجازهٔ استفاده از APIهای احرازشده ندارد.
- خروج از حساب همچنان مجاز است. حذف توکن شخصی از خروج نشست کوکی تفکیک شده تا توکن موقت Sanctum موجب خطای خروج نشود.
- ورود حساب pending و وضعیت ناشناخته رد می‌شود؛ حساب با نقش غیرفعال می‌تواند احراز هویت شود اما **هیچ مجوزی از آن نقش نمی‌گیرد**. استثناهای رابطه‌ای محدود، مانند عضویت گفتگو، با غیرفعال‌شدن نقش به‌تنهایی حذف نمی‌شوند؛ برای قطع همهٔ دسترسی‌ها حساب را مسدود کنید.
- هویت نقش از رابطهٔ `role_id` به Role خوانده می‌شود، نه `role_key` قدیمی. نقش مفقود/غیرفعال و حساب غیرفعال قدرت مدیر سیستم نمی‌دهند.
- خروجی پروفایل `roleIsActive` دارد. fallback بازِ فرانت حذف شده: نبودن یا خالی‌بودن مجوزها به معنی اجازه نیست. این اصلاح فقط helper مشترک UI است؛ پاک‌سازی کامل cache و تمام شرط‌های قدیمی UI هنوز کار جداگانه می‌خواهد.

### حساب‌های کاربری و مدیریت نقش‌ها

- `users.status` به‌تنهایی برای تغییر وضعیت کافی است، ولی اجازهٔ ویرایش نام/رمز/نقش نمی‌دهد؛ درخواست ترکیبی غیرمجاز به‌طور کامل رد می‌شود.
- ویرایش شخصی محدود به فیلدهای پروفایل است. تغییر نقش خود برای غیرمدیر رد می‌شود.
- انتساب نقش به حساب دیگر نیازمند `users.edit` و `roles.manage_permissions` است؛ در ساخت حساب، `users.create` و اختیار واگذاری نقش لازم است. غیرمدیر فقط نقش غیرسیستمی در محدودهٔ مجوزهای خودش را می‌تواند واگذار کند. نقش قبلی پرقدرت نیز با یک نقش ضعیف قابل جایگزینی توسط مدیر محدود نیست.
- دست‌کاری حساب مدیر سیستم، از جمله تغییر رمز، توسط ویرایشگر عادی کاربران بسته شده است.
- نقش‌های ویژهٔ `admin` و `content_manager` از انتساب/تغییر نام غیرمدیر محافظت می‌شوند. این حفاظت **به معنی پیاده‌سازی ACL محتوای content_manager نیست**.
- تناقض `role` و `roleId` یا نقش نامعتبر با ۴۲۲ رد می‌شود؛ شناسهٔ نامعتبر بی‌صدا نادیده گرفته نمی‌شود.
- غیرفعال‌سازی/تنزل آخرین مدیر فعال و حذف نقش دارای کاربر رد می‌شود. مسیرهای تغییر/حذف حساب از قفل مشترک نقش مدیر در تراکنش استفاده می‌کنند. نقش admin قابل غیرفعال‌کردن نیست.
- ویرایش پویای مجوزها از مسیر فعلی نقش‌ها همچنان وجود دارد، اما کلید ناشناخته/تکراری و واگذاری مجوزی بالاتر از مجوز خود شخص رد می‌شود. تغییر فعال‌بودن یا کلید نقش نیز عملیات امنیتی است، نه ویرایش سادهٔ عنوان.
- تغییرهای نقش و حساب روی سرور ثبت فعالیت می‌شوند؛ رمز/توکن در جزئیات ثبت نمی‌شود. جایگزین‌کردن سیستم فعالیت فعلی با audit غیرقابل‌جعل/مجزا هنوز انجام نشده است.

### وظایف

- PUT/PATCH عمومی از `TaskOperations::updateFields` استفاده می‌کند. داشتن یکی از مجوزهای endpoint دیگر کافی نیست: **فیلد تغییرکرده** کنترل می‌شود.
- تغییر مسئول: `tasks.assign`؛ تغییر وضعیت: `tasks.status` یا استثنای قبلیِ مسئول همان وظیفه؛ سایر تغییرها: `tasks.edit`. مشاهدهٔ وظایف نیز لازم است.
- استثنای مسئول روی مسئول ذخیره‌شده سنجیده می‌شود؛ ارسال هم‌زمان «مسئول = خودم» و «تکمیل» راه دورزدن نیست.
- درخواست ترکیبی غیرمجاز هیچ تغییر جزئی ثبت نمی‌کند. مقادیر بدون تغییر در roundtrip مجوز اضافی لازم ندارند. وضعیت از سرویس مشترک قبلی عبور می‌کند و JSON برچسب/وابستگی دوباره encode نمی‌شود.
- این مرحله scope سراسری فعلی وظایف/پروژه‌ها یا ACL وظایف وابسته به محتوا را بازطراحی نمی‌کند.

### پیام‌ها و گفتگوها

- `ChatAccess` منبع مشترک عضویت برای فهرست، جزئیات، ویرایش، حذف تکی و حذف دسته‌ای است. فیلتر conversation_id مجوز نیست. شناسه‌های عددی و رشته‌ای قدیمی در memberIds پشتیبانی می‌شوند.
- **بدون عضویت، حتی مدیر سیستم/مدیر پیام‌رسان نیز دسترسی خودکار به متن خصوصی ندارد.** این حداقل محافظت امنیتی این مرحله است؛ قابلیت استثنایی ورود اضطراریِ ثبت‌شده هنوز ساخته نشده است.
- نویسنده/سازنده روی سرور از حساب جاری تعیین می‌شود. parent و sender پیام از مسیر ویرایش عمومی قابل تغییر نیستند؛ متن فقط توسط نویسنده و عضو فعلی ویرایش می‌شود.
- ساخت گفتگو `messaging.create_chat` و ارسال پیام `messaging.send_message` می‌خواهد؛ ارسال علاوه بر آن عضویت و تنظیم writePermission را بررسی می‌کند. پاسخ به پیامِ گفتگوی دیگر پذیرفته نمی‌شود.
- عضو عادی نمی‌تواند خودش را مدیر کند یا عضو جدید اضافه کند؛ مدیر گفتگو از دادهٔ ذخیره‌شده و پس از کنترل عضویت تشخیص داده می‌شود. سازنده عضو باقی می‌ماند؛ اعضای گفتگوی مستقیم قابل تعویض نیستند.
- حذف دسته‌ای پیش از هر حذف تمام رکوردها را کنترل می‌کند و all-or-nothing است. حذف گفتگو پیام‌های وابسته را نیز در همان تراکنش حذف می‌کند.
- تغییر گروهی reaction/read receipt یا جعل metadata از PUT عمومی پذیرفته نمی‌شود. عملیات مستقل، ترجیحات شخصی و اتصال API-first کامل رابط چت **در این مرحله پیاده نشده‌اند**؛ چند عمل UI قبلی هنوز محلی هستند. به همین دلیل این خروجی «پیام‌رسان آمادهٔ بهره‌برداری کامل» نامیده نمی‌شود.

## استقرار روی هاست اشتراکی

- این مرحله migration جدید، Cron، SSH یا وابستگی production جدید ندارد. اصلاحات **بک‌اند** و build فرانت باید هر دو مستقر شوند؛ کپی‌کردن فقط dist کنترل امنیتی سرور ایجاد نمی‌کند.
- build production با آدرس API واقعی در `frontend/dist/` نگه داشته شده و از Git ignore خارج باقی مانده است. محتویات این پوشه برای ریشهٔ سایت فرانت است؛ سورس بک‌اند مطابق ساختار فعلی هاست نصب شود.
- پیش از انتشار، بکاپ بگیرید و با دسترسی مدیریتی موجود هاست/phpMyAdmin، کوئری‌های فقط‌خواندنی `access-control-phase1-preflight.mysql.sql` را بررسی کنید. دادهٔ ناسازگار role_id/role_key نباید با اعطای خودکار admin «ترمیم» شود. حداقل یک حساب active با رابطهٔ واقعی به نقش فعال admin لازم است.
- گفتگوهای قدیمی بدون memberIds معتبر، بعد از اصلاح برای کسی که عضو محسوب نمی‌شود پنهان خواهند بود. چون نسخهٔ قبلی امکان جعل این آرایه را داشت، فهرست اعضای قدیمی نیز نیازمند بازبینی مدیریتی است؛ از صحت تاریخی آن‌ها مطمئن نیستیم.
- پاک‌سازی cacheهای تنظیمات/route/opcode فقط با روش امن و موجودِ مدیریت هاست انجام شود؛ endpoint عمومی تعمیر/اجرای فرمان ایجاد نکنید. `.env` هاست را جایگزین یا منتشر نکنید.
- smoke test با دو کاربر مجزا: حساب مسدود با توکن قبلی، تغییر نقش غیرمجاز، درخواست ترکیبی وظیفه، مشاهدهٔ پیام غیرعضو، حذف دسته‌ای مخلوط و خروج حساب مسدود.
- rollback هم‌زمان سورس و dist ممکن است آسیب‌پذیری‌های قبلی را برگرداند؛ rollback امنیتی را بی‌خطر فرض نکنید.

## ادامهٔ کار (انجام نشده)

۱. Policy/scope مشترک محتوا با قاعدهٔ قطعی **دپارتمان OR تیم** و ویرایش عادی مستقل از نقش، مدیر محتوای سراسری، تأیید/انتشار مستقل؛ همراه وظیفه، فایل، جدول، اعلان، فعالیت و خروجی وابسته. پیش از فعال‌کردن grant دپارتمان، ادعای دپارتمان در ثبت‌نام عمومی نیز باید از عضویت تأییدشده جدا شود.
۲. رأی‌گیری به‌صورت فرمان شخصی و غیرقابل‌جایگزینیِ رأی دیگران؛ scope فعالیت‌ها و ثبت وقایع معتبر سرور.
۳. scope پروژه/وظیفه، سیاست وراثت دپارتمان و پوشش DAM/Bale/اعلان‌ها/خروجی‌ها با یک Policy مشترک.
۴. ویرایشگر پویای «عملیات + دامنه + رابطه»، توضیح علت مجاز/ردشدن، نسخه‌بندی و پیش‌نمایش اثر تغییر. این UI جدید هنوز ساخته نشده است.
۵. cache isolation، UI capabilities و تکمیل API-first چت، از جمله عملیات مستقل reaction/read receipt.

تصمیم‌های باز گزارش قبلی (scope مرتبط پروژه/وظیفه، وراثت دپارتمان، دپارتمان اصلی در برابر مراحل تولید، شکل break-glass پیام خصوصی) حذف نشده‌اند. این مرحله برای اجرای بخش‌های قطعی منتظر پاسخ به آن‌ها نمانده، اما باقی سیاست‌ها را خودسرانه کامل‌شده فرض نکرده است.

## ثبت نهایی اجرای محلی

- تست‌های رگرسیون جدید: **۳۸ تست / ۱۰۰ assertion، همگی پاس**.
- کل مجموعهٔ عادی بک‌اند: **۱۶۴ تست / ۷۸۷ assertion، همگی پاس**؛ شامل تست‌های قبلی Bale. محیط: PHP 8.5.10 WASM، PHPUnit 12.5.35 و SQLite حافظه‌ای. برای اجرای مجموعهٔ قدیمی در WASM، mockConsoleOutput موقتاً غیرفعال و بلافاصله فایل TestCase اصلی بازگردانده شد؛ این تنظیم وارد سورس production نشده است.
- ممیزی جداگانه: **۱۶ تست / ۱۷ assertion، ۵ شکستِ باز، بدون error**؛ ۱۱ پروب پاس.
- TypeScript: پاس. تست‌های Node فرانت: **۱۱/۱۱ پاس**. Pint فایل‌های PHP تغییریافته: پاس.
- build production: پاس، ۲۶۸۸ ماژول؛ هشدار شناخته‌شدهٔ بزرگ‌بودن bundle باقی است. ارجاع assetهای HTML، آدرس API production و نبود source map کنترل شد.
- خروجی جدید: `frontend/dist/assets/index-BNuTBpBz.js` و `index-mPWAHIua.css` همراه `index.html` و favicon.
- **هیچ تست زنده روی هاست، MySQL چندپردازه، مرورگر واقعی یا بلهٔ زنده اجرا نشده؛ هیچ استقراری روی هاست انجام نشده است.** کوئری preflight روی دیتابیس هاست اجرا نشده است.

### اصلاح تکمیلی حفاظت فایل محیطی

در بررسی نهایی مشخص شد `backend/.env` برخلاف انتظار **از قبل tracked بود**؛ ignore روی فایل tracked اثر ندارد. این فایل از index گیت خارج شد و نسخهٔ محلی حذف نشد؛ `.gitignore` اکنون می‌تواند از ثبت مجدد معمول آن جلوگیری کند. فایل نمونهٔ `.env.example` باقی است. این حذف، رازهای احتمالی موجود در تاریخچهٔ قبلی را پاک نمی‌کند. اگر تنظیمات این فایل واقعی/فعال بوده‌اند، مسئول استقرار باید رمزهای مربوط را تعویض کند؛ **APP_KEY را بدون برنامهٔ حفظ/بازرمزگذاری داده‌های رمز‌شده، از جمله تنظیمات بله، عوض نکنید**. هیچ مقداری از فایل در این گزارش درج نشده و هیچ اعتبارنامه‌ای روی هاست تغییر نکرده است.
