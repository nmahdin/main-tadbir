# گزارش بهینه‌سازی سرعت و مصرف اینترنت — دور ۸۳ (به‌روزشده در دور ۸۴)

> **دور ۸۴:** دو مورد از اولویت‌های این گزارش اجرا شد: «بندانگشتی سمت سرور» و
> «ETag روی GETهای فهرست». جزئیاتشان در بخش ۸ آمده است.

> دامنهٔ بررسی: کلاینت `frontend/` (Vite + React) و مسیرهای شبکه‌ای که همین کلاینت صدا می‌زند.
> عددها از خروجی ساخت تولیدی همین نسخه (`npm run build`) و کد فعلی گرفته شده‌اند.

## ۱) تصویر کلی: صفحهٔ اول چه چیزی دانلود می‌کند؟

| قلم | حجم خام | حجم gzip |
| --- | --- | --- |
| `index.html` | ۲.۷ KB | ۱.۱ KB |
| `index-*.js` (کد برنامه) | ۲۷۸ KB | ۸۰ KB |
| `react-vendor-*.js` (React + Router) | ۲۶۴ KB | ۸۴ KB |
| `query-vendor-*.js` (React Query) | ۴۱ KB | ۱۲ KB |
| `index-*.css` (کل استایل) | ۱۷۶ KB | ۲۶ KB |
| فونت وزیرمتن (زیرمجموعهٔ عربی) | ۴۶ KB | — |
| **جمع تقریبی صفحهٔ ورود/داشبورد** | **≈ ۸۰۸ KB** | **≈ ۲۰۳ KB** |

نکات مثبت تأییدشده:

* ۴۰ نمای صفحه و همهٔ مدال‌ها با `React.lazy` بیرون از بستهٔ اولیه‌اند؛ هر مسیر فقط بستهٔ خودش را می‌گیرد (۱۴۴ فایل JS جدا).
* فونت با `unicode-range` تقسیم شده است؛ فارسی‌زبان فقط زیرمجموعهٔ عربی (۴۶ KB) را می‌گیرد، نه لاتین/لاتین‌اکستند (۶۰ KB) را.
* `QueryClient` با `staleTime: 30s`, `gcTime: 300s`, `refetchOnWindowFocus: false` و حداکثر **یک** تلاش مجدد تنظیم شده است.
* بارگذاری داده «مسیرمحور» است (`VIEW_MODULES`): باز کردن کارتابل، چت، امنیت یا گزارش‌ها را دانلود نمی‌کند.
* جست‌وجوی سراسری دیبانس ۲۲۰ms دارد و پیش از دو حرف هیچ درخواستی نمی‌فرستد.
* تصاویر با `loading="lazy"`, `decoding="async"` و فقط **یک** درخواست در هر تصویر رندر می‌شوند (`SmartImage`).
* کارت‌های خروجی محتوا (دور ۸۲) صفر درخواست دارند؛ تصویر/متن فقط با باز شدن مدال گرفته می‌شود.

## ۳) پرریسک‌ترین منبع مصرف اینترنت (اجرا شد — دور ۸۴)

**بندانگشتی‌های مخزن، فایل اصلی را دانلود می‌کردند.**

`AssetThumbnail` و کارت‌های مخزن نشانی `…/preview` (فایل کامل) را می‌گرفتند؛ یک جدول ۲۰ ردیفی از تصاویر موبایلی می‌توانست ۲۰–۶۰ مگابایت دانلود کند برای کادرهای ۴۰ پیکسلی.

اصلاح انجام‌شده:

1. مسیر تازهٔ `GET /api/v1/dam/library/{asset}/thumbnail?w=96|160|320|640` با سرویس `App\Support\Media\DamThumbnail`؛ نسخهٔ کوچک یک‌بار ساخته و روی `storage/app/public/dam-thumbnails` کش می‌شود (WebP در صورت پشتیبانی Imagick/GD، وگرنه JPEG).
2. پاسخ با `Cache-Control: private, max-age=604800` و `ETag` می‌آید؛ درخواست تکراری مرورگر ۳۰۴ بدون بدنه می‌گیرد.
3. اگر سرور هیچ افزونهٔ تصویری نداشته باشد، همان فایل اصلی با همان هدرهای کش سرو می‌شود (بندانگشتی خالی نمی‌ماند).
4. کلاینت: کارت شبکه‌ای `w=320` و ردیف/جزئیات `w=96` می‌گیرد؛ پیش‌بارگذاری فایل کامل با هاور از کارت حذف شد و تصویر کامل فقط با باز شدن مدال دانلود می‌شود.

## ۵) کارهایی که ارزش انجام دادن ندارند (بررسی و رد شد)

* **حذف React Query یا جایگزینی آن**: کش مشترک، حذف درخواست‌های تکراری و `keepPreviousData` را از دست می‌دهیم.
* **Service Worker برای کش API**: داده‌های سازمانی حساس‌اند و سیاست دسترسی پویاست؛ ریسک کهنگی/نشتی بیشتر از سود آن است.
* **بارگذاری تصویر «بلور‌شدهٔ» جداگانه (LQIP)**: یک درخواست دوم برای هر تصویر می‌سازد — خلاف هدف کاهش مصرف.
* **کاهش `staleTime`های فعلی**: درخواست بیشتر می‌شود، نه کمتر.

## ۶) چگونه اندازه بگیریم

```bash
cd frontend
npm run build                # اندازهٔ بسته‌ها و چانک‌ها
node --test tests/*.mjs      # تست‌های قراردادیِ رفتار (شامل تست‌های همین دور)
```

در مرورگر: DevTools → Network با «Disable cache» و پروفایل «Slow 4G»؛ سه عدد کلیدی:
زمان اولین درخواست API (باید بدون TLS handshake اضافه باشد)، حجم صفحهٔ اول (~۲۰۰ KB gzip) و تعداد درخواست‌های تب پنهان (باید صفر باشد).

## ۷) خلاصهٔ یک‌خطی

صفحهٔ اول با ~۲۰۰ کیلوبایت gzip و بدون درخواست پس‌زمینهٔ اضافی بالا می‌آید؛ بزرگ‌ترین اتلاف (دانلود فایل کامل برای بندانگشتی‌های مخزن) در دور ۸۴ با مسیر بندانگشتی کش‌شده برطرف شد و پاسخ‌های تکراری API هم با ETag به ۳۰۴ تبدیل می‌شوند.

## ۸) جزئیات اجرای دور ۸۴

* **بندانگشتی:** `DamThumbnail` و متد `thumbnail` در `DamAssetController`؛ مسیر در `routes/api.php`. اندازه‌های مجاز ثابت‌اند (۹۶/۱۶۰/۳۲۰/۶۴۰) تا کش با اندازه‌های بی‌نهایت پر نشود و مقدار نامعتبر به ۳۲۰ برمی‌گردد. نام فایل کش شامل حجم + checksum + زمان تغییر نسخه است؛ پس ویرایش فایل، بندانگشتی تازه می‌سازد.
* **کش شرطی:** میدل‌ور `ConditionalJsonCache` روی گروه `api`؛ فقط `GET/HEAD` با پاسخ `200` و `JsonResponse`. پاسخ‌هایی که خودشان `no-store` اعلام کرده‌اند (مثل وضعیت حساب بله) دست‌نخورده می‌مانند. هدر `Cache-Control: private, no-cache` می‌ماند تا هیچ پراکسی مشترکی دادهٔ سازمانی را نگه ندارد.
* **اثر انتظاری:** با تصاویر، حجم فهرست مخزن از چند ده مگابایت به چند صد کیلوبایت می‌رسد؛ در درخواست‌های تکراریِ بدون تغییر، بایت بدنه صفر می‌شود.
