# TADBIR Comprehensive — Core v1 Architecture Specification (Design Freeze Candidate)

- **Status:** PROPOSED — design-only stage on baseline `7b90a73` (Stages 01–04B incl. 04B hardening). Nothing in this document is implemented by this stage; implementation begins only after human approval, stage by stage (`docs/roadmap/core-v1-completion-roadmap.md`).
- **Authority:** On approval, this is the single authoritative Core v1 design. It refines (does not replace) `core.md` (Stage 01 target direction) and ADR-0001…0012; conflicts are listed explicitly in `core-design-review-report.md`.
- **Vocabulary:** CONFIRMED = present in code at `7b90a73` with tests. PROPOSED = recommended here, binding only after approval. OPEN = requires a named human decision (register in `docs/migration/decisions-and-open-questions.md`).

## 0. Design principles (reaffirmed, binding from earlier stages)

1. Modular monolith: one Laravel deployment + React SPA; modules own code and tables; cross-module interaction only through `Contracts/` interfaces or domain events; no direct writes into another module's tables; Core depends on no business module (ADR-0001).
2. Workspace is the strict operational boundary; every operational record belongs to exactly one workspace; a client-supplied `workspace_id` is never proof of access (ADR-0002/0008).
3. One central authorization decision (`AuthorizationService`, Stage 04A) for HTTP, console, queues, Bale, and Google adapters; deny-by-default; fail closed on unimplemented gates.
4. Laravel-native patterns first; no speculative abstraction; every seam must serve a named current need (CODING_STANDARDS §1.7).
5. Shared-hosting operability is a hard constraint: no assumed workers, SSH, or Cron; `vendor/`/`dist` are tracked release artifacts (ADR-0011).
6. SQLite (dev/CI) and MySQL (production profile) parity: domain validation enforces every invariant on both engines; DB constraints added where the verified engine supports them (ADR-0009).

## A. Identity and accounts

**CONFIRMED:** `users` is the single platform identity (username-based accounts exist, `docs/username-accounts.md`; Sanctum tokens); `users.status ∈ active/inactive/blocked/pending` (legacy enum, MySQL native ENUM); `EnsureActiveAccount`-equivalent behavior re-checked in the authorization resolver (Stage 04A); legacy `role_id/role_key/department_id` columns still present and authoritative for unmigrated modules only.

**PROPOSED (Core v1):**
- **Account lifecycle:** statuses normalize to `active / suspended / deactivated` (PROPOSED mapping: legacy `inactive`→`suspended` (reversible, platform action), `blocked`→`suspended` with a `suspension_reason`, `pending` retained only if an approval flow is approved — recommendation: drop `pending` in v1; registration is either open or invite-only, see §C). Deactivation is terminal for access but preserves historical ownership: memberships end (not delete), authored records keep `created_by`, and the account row is retained (FK RESTRICT pattern from Stage 03A).
- **Authentication boundary:** Core owns credential verification, token issuance/revocation, and session invalidation on suspension. Adapters (Bale/Google) never authenticate independently; they link an external identity to a `users` row (existing `bale_user_links`/`google_workspace_links` precedent) and then call the same authorization decision.
- **Personal default workspace:** created lazily and idempotently by `PersonalWorkspaceProvisioner` on first need (CONFIRMED pattern, Stage 03A/04A usage); exactly one default personal workspace per user (DB discriminator unique index, CONFIRMED).
- **Multi-organization membership:** a user may hold independent memberships in many organizations and workspaces; no membership implies another (ADR-0003, CONFIRMED).
- **Workspace selection/switching:** stateless: the client sends a workspace identifier per request (header or input) as a *lookup key*; the server re-resolves context on every call (CONFIRMED, Stage 04A). A "current workspace" UI preference may be stored client-side or as a user preference (non-authoritative; §F user settings) — it never grants access.
- **Platform administration:** a platform-scope role set distinct from organization/workspace roles (see §D); platform administrators get **no implicit workspace context** (CONFIRMED behavior in resolver; Q-10 proposal in register).

## B. Organizations and workspaces

**CONFIRMED:** `OrganizationProvisioner` atomically creates organization + default organizational workspace + creator org membership (Organization Manager) + explicit workspace membership (Workspace Manager) (Stage 03A/03B). Workspace XOR ownership enforced in model on both engines + MySQL CHECK; one-default-per-owner via generated discriminator columns; membership uniqueness for live memberships likewise. Workspace status string `active/suspended` honored by the resolver. Organization responses expose organization-plane data only (Stage 03A correction).

**PROPOSED (Core v1):**
- **Lifecycle:** organizations and workspaces share the status vocabulary `active / suspended / archived`. Suspended = reversible platform/org-manager action; all operational access denied while suspended (resolver already denies non-active workspaces; organization suspension check is added at decision step 2, §Decision Spec). Archived = terminal read-only retention state; records preserved; no new memberships; deletion is a separate, explicitly authorized platform operation (v1: no hard delete of organizations/workspaces with records — FK RESTRICT precedent).
- **Creation:** personal workspace creation is owner-only, subject to plan workspace quota (§E). Organizational workspace creation requires `organization.workspaces.create` (CONFIRMED key) + organization Manager-equivalent authority for manager assignment; creator does **not** automatically receive a workspace membership except for the one default workspace at organization creation (CONFIRMED) — additional workspaces: creator may add themselves explicitly as a member (self-join rule §C).
- **Access revocation:** ending/deactivating a workspace membership revokes operational access immediately (per-call re-resolution, CONFIRMED). Ending an organization membership cascades logically: org-workspace contexts deny at the organization-membership step even if the workspace membership row is still active (CONFIRMED decision order); the workspace membership rows are ended in the same transaction for hygiene (PROPOSED service rule).
- **Quotas:** enforced at creation/invitation-acceptance time by the entitlement evaluator (§E): workspaces per owner, members per workspace, storage per workspace. Over-limit creation denies with 403 `quota_exceeded` category; existing data is never deleted by quota enforcement.

## C. Members, invitations, departments

**CONFIRMED:** membership lifecycle `active → deactivated → active`, `active/deactivated → ended` (terminal); rejoin = new row (ended rows preserved as history); live-uniqueness per (scope, user) via discriminator columns; `end()` clears the role; final-manager guard with scope-row-first locking, MySQL-proven (Stage 03B). **No invitation system exists** (Q-08 OPEN). Legacy departments are installation-global with `parent_id` hierarchy + `department_user` pivot with free-text role (to be replaced, ADR-0006).

**PROPOSED (Core v1):**
- **Invitations (new Core service, `Core\Invitations`):** invitation = one row (`invitations`): scope (`organization` or `workspace`), target scope id, invitee identifier (email **or** phone **or** existing username — exactly one, normalized), invited role id (scope-matching, grant-ceiling-checked at invite time), status `pending/accepted/expired/cancelled`, `expires_at` (default 7 days, PROPOSED — human may change), single-use random token stored **hashed**; acceptance is an authenticated, idempotent operation: (a) resolves invitee account (existing account matched by verified identifier; unregistered invitee registers first, identifier verified by the channel that carried the invitation — OTP for phone, signed link for email — verification mechanics are PROPOSED defaults, see open decision OD-3); (b) accepting a *workspace* invitation to an organizational workspace creates the organization membership automatically (Member default org role) if none exists — this is the **only** implicit org-membership acquisition path; (c) creates/rejoins the membership with the invited role; (d) checks membership quota before activation. Invitation creation/cancellation requires `*.members.manage` in the target scope; grant ceiling applies to the invited role (inviter cannot invite above their own authority); final-manager rules unaffected.
- **Self-joining:** organization managers may add **themselves** to a workspace of their organization only with an explicit workspace role assignment recorded as a normal membership (audited); they receive no data access before that assignment exists. No other self-join path in v1.
- **Departments (Core v1 model):** workspace-scoped and flat (ADR-0006): `workspace_departments` (workspace_id, name, manager_user_id nullable) + `workspace_department_members` (department_id, user_id, `is_primary` boolean, unique (department, user); at most one primary per (workspace, user) enforced by service + partial unique discriminator). Membership in a department requires an active workspace membership (service rule on add/accept and on membership end → department rows removed in the same transaction). Departments are grouping/responsibility only — **never** an authorization boundary and never a substitute for workspace membership. Manager succession: department manager is a plain pointer; when that user leaves the workspace, the pointer nulls and a Workspace Manager reassigns (no last-manager invariant for departments; the invariant protects *workspace* managers only, §D).
- **Legacy removal:** `departments`, `department_user`, `users.department_id`, `teams*` are deleted at the Departments cutover stage only after the workspace-scoped replacement + dependent analytics (Q-07 recommendation: keep `is_primary` flag; department analytics recompute from it) are implemented and tested (roadmap stage C6).

## D. RBAC and central authorization

**CONFIRMED (Stages 03B/04A/04B):** scoped roles (`organization`/`workspace`; platform scope intentionally absent), exactly one role per active membership, protected per-scope Manager/Member defaults materialized from the code-canonical `PermissionCatalog`, custom workspace roles under grant ceiling, unknown/cross-scope keys rejected (422), final-manager invariant under scope-row-first locking (MySQL concurrency-proven), central decision order with distinct failure reasons, `WorkspaceScope` IDOR-safe record assertions, one consumer migrated (Projects pilot with pilot gates).

**PROPOSED (Core v1 completions):**
- **Module permission ownership:** each module registers its keys in the Core catalog via its manifest (`PermissionCatalog` remains the single canonical registry; module manifests declare the keys, catalog materializes them — replacing today's hand-edited catalog constants with manifest-driven registration in the Module Lifecycle stage, roadmap C7; keys and scopes unchanged).
- **Platform administrators:** add `platform` scope to the catalog with a minimal key set (`platform.organizations.view/suspend`, `platform.users.view/suspend`, `platform.plans.manage`, `platform.modules.manage`, `platform.settings.manage`, `platform.audit.view`) assigned via a `platform_role_assignments` table (user_id, role key) — deliberately **not** a membership; platform roles never resolve a workspace context and never satisfy membership steps (PROPOSED; Q-10 decision required, OD-1).
- **Organization role templates (Q-06):** `organization_role_templates` (org, name, permission keys snapshot) + workspace roles may record `template_id + template_version`. Propagation is explicit: an org manager triggers "apply template" per workspace → preview diff → confirm → atomic per-workspace role update in one transaction; no silent background propagation; workspaces may detach (template_id=null) at any time. (PROPOSED; post-v1 acceptable — listed as v1-optional in capability matrix.)
- **Surfaces:** HTTP (CONFIRMED), console/queue/Bale/Google: adapters resolve the same `AuthorizationService` with an explicit actor + workspace identifier; **no cached contexts in jobs** — a queued/triggered job re-resolves at execution time and fails closed if memberships changed since enqueue (ADR-0011 tick model).
- **Authorization audit events:** every management-plane mutation (membership/role/invitation/plan/policy/settings) writes an `audit_logs` row (§I); denied *operational* decisions are counted/sampled, not row-per-denial (volume), except gate denials in production which are logged (PROPOSED).
- **Final-manager guarantee:** unchanged (scope container row `FOR UPDATE` before membership/role locks on every removal path; MySQL tests are the only locking proof; SQLite proves sequential semantics only).

## E. Plans, subscriptions, entitlements

**CONFIRMED:** ADR-0010 direction: entitlement ≠ org policy ≠ workspace activation ≠ permission; new features default-disabled in plans; payments ≠ subscription; manual activation first. No billing code exists. Q-01 OPEN until this design.

**PROPOSED v1 model (resolves Q-01 as a proposal; business-policy items flagged OD-2):**
- **Plans:** platform-defined `plans` (scope: `personal`|`organization`, name, status `draft/active/retired`) with immutable **versions** (`plan_versions`: version no., limits JSON — max_workspaces, max_members_per_workspace, storage_bytes, per-module entitlement map `{module_id: enabled}`, feature capabilities map, price snapshot fields `price_amount/currency/period_months`). Editing a plan creates a new version; existing subscriptions keep their version until changed (no silent repricing).
- **Subscriptions:** one *effective* subscription per subscriber: personal → `subscriptions.subscriber_user_id` (covers that user's **personal** workspaces only); organization → `subscriptions.subscriber_organization_id` (covers **all** its workspaces). Status machine (PROPOSED): `pending → active → past_due → suspended → expired`, plus `cancelled` (terminal, effective at period end) — see Decision Spec §5 for read/write behavior per status. `period_start/period_end`, `auto_renew=false` in v1 (**manual renewal only**: renewal = explicit action creating the next period, recorded in `subscription_events`). Personal-extra-workspace billing edges: personal plan workspace quota counts personal workspaces only; organizational workspaces never consume personal quota.
- **Entitlements evaluation:** effective entitlement = plan-version module map ∩ platform module state (§F) — a module not enabled in the subscriber's plan version is unavailable regardless of workspace activation. **New modules/features default to disabled** in every existing plan version (map absence = disabled).
- **Upgrade/downgrade:** preview computes (a) price delta snapshot, (b) limit impacts (which workspaces/members/storage would be over-limit); downgrade requires explicit confirmation and never deletes data: over-limit entities become read-only/frozen at the limit boundary (cannot add, existing remain readable) — exact freeze semantics per limit type in Decision Spec §6. Changes apply at confirmation (upgrade) or at period end (downgrade) — PROPOSED default, OD-2.
- **Payments separation:** `payment_attempts` (future payment adapter writes attempts; success *activates/renews* via the subscription service API only). No payment provider in v1; manual activation by platform admin (`platform.plans.manage`) with audit event.
- **Precedence:** platform kill-switch > organization policy ceiling > subscription entitlement > workspace activation > role permission (all must allow; Decision Spec).

## F. Settings and module activation

**CONFIRMED:** legacy global `system_settings` table only; no scoped settings exist. `ModuleRegistry` + manifests exist; `ProjectsModule` manifest unregistered; no activation tables.

**PROPOSED:**
- **Settings:** one `core_settings` table (scope_type `platform|organization|workspace|user`, scope_id, key, value JSON, `is_sensitive` → encrypted at rest, updated_by) backed by a code registry declaring per key: allowed scopes, type/validation, default, `overridable` flag. Resolution: workspace → organization → platform → registry default; a higher scope may mark a value **mandatory** (lower scopes cannot override). Sensitive values are never returned to lower-privilege readers and are audit-logged on change. Module settings live under the module's key prefix and are read through the same service. User preferences (theme, current workspace hint, notification prefs pointer) are `user`-scope rows — never authorization inputs.
- **Module activation:** `module_definitions` materialized from manifests (id, version); `workspace_modules` (workspace_id, module_id, state `enabled/disabled`, set by Workspace Manager with `workspace.manage` + additionally organization Managers may *restrict* (disable/ceiling) via `organization_module_policies` (organization_id, module_id, max_state). Effective availability = platform definition active ∧ org policy allows ∧ plan entitles (§E) ∧ workspace enabled. Activation changes are audit-logged; disabling a module never deletes its data.

## G. Shared file infrastructure (Files Core)

**CONFIRMED:** DAM owns `dam_files`/assets today with its own access checks; task attachments exist; no Core file service; signed-link semantics OPEN (Q-09).

**PROPOSED:** `Core\Files` owns *storage mechanics and access mediation only*: `files` table (id, workspace_id NOT NULL, storage_disk/path, mime, size_bytes, checksum, uploaded_by, status `active/pending_delete/deleted`, timestamps) + `file_links` (file_id, owner module + record reference, purpose) so modules attach meaning while Core mediates every download: authorization = resolve context from the **linked record's** workspace + module permission, checked per download (no permanent public URLs). Upload pipeline: size/mime allowlist validation, checksum, quota debit against the workspace storage limit (§E); orphan cleanup via triggered tick (ADR-0011). Signed links: short TTL (PROPOSED 15 min), single-workspace, revoked implicitly when the file is deleted or the link's `revocation_epoch` changes (workspace suspension bumps epoch — resolves Q-09 as PROPOSED: revocation invalidates outstanding links). Retention: soft-delete → `pending_delete` → physical purge by tick after 30 days (PROPOSED default, OD-4). DAM remains a business module consuming Files; its asset/version semantics stay in DAM.

## H. Notifications

**CONFIRMED:** legacy `NotificationInbox`/`domain_records(notification)` and Bale notification classes; no Core inbox service.

**PROPOSED:** `Core\Notifications`: `notifications` (id, user_id, workspace_id nullable, type key, payload JSON with record references — never authorization data, read_at, created_at) written by module events through a Core contract; inbox reads are per-user (no workspace grant implied; payload references are re-authorized when the user follows them). Preferences: user-scope settings (§F) per channel (`in_app` always on; `bale`, `email` opt-in where linked). Delivery: adapters (in-app = the row itself; Bale/email = outbox-style `notification_deliveries` with attempts, exponential backoff by tick, terminal `failed` state visible in admin view). Recipient authorization: producers may only notify users who are active members of the event's workspace (validated at send time; membership loss before delivery cancels external deliveries, inbox rows remain but deep links re-authorize and deny).

## I. Audit and activity

**CONFIRMED:** `activity_logs` = user-facing feed (retained); **no** audit log exists (D-18 accepted, unimplemented).

**PROPOSED — three distinct streams:**
1. **Audit (`audit_logs`, Core, append-only):** security/management events — account status, membership/invitation/role/permission, organization/workspace lifecycle, plan/subscription/policy/settings changes, file signed-link issuance, platform-admin actions. Columns: actor_user_id, actor_context (scope type/id, workspace/organization id), action key, target reference, redacted before/after summary (sensitive fields masked by key registry), ip/user-agent where available, created_at. No update/delete paths in code; retention PROPOSED ≥ 1 year platform-configurable (OD-4).
2. **Activity (`activity_logs`, module-owned feeds):** user-facing, workspace-scoped when the subject is workspace-owned; may be pruned by module policy; never used for security decisions.
3. **Application logs:** Laravel log channels; must never contain tokens, invitation secrets, or file contents (masking rule in CODING_STANDARDS addendum proposal).

Audit writes occur in the same transaction as the mutation they record (management plane) — an unauditable management change fails.

## J. Events and background processing

**CONFIRMED:** `QUEUE_CONNECTION=sync`; Bale outbox precedent; ADR-0011 (sync default + idempotent triggerable ticks; outbox only for proven-critical events).

**PROPOSED:** module domain events are plain, versioned DTO classes in the publisher's `Events/` folder, dispatched **after commit** (`DB::afterCommit`) for synchronous listeners; cross-module reactions that must survive failure use the transactional outbox (`core_outbox`: event key, payload, workspace_id, attempts, available_at, processed_at) drained by an externally triggered, idempotent tick endpoint/command (shared-hosting model). Every consumer is idempotent via `event_id` dedupe. Retry: 5 attempts with backoff, then `dead` + audit entry. Modules never call another module's write services inside the publisher's transaction except through `Contracts/` synchronous queries explicitly documented as such.

## K. Module lifecycle and public contracts

**CONFIRMED:** `ModuleManifest`/`ModuleRegistry` (id + permission keys), architecture tests enforce: Core ↛ Modules/Integrations, Modules ↛ Integrations, cross-module imports only via `Contracts\`, every module dir has a manifest provider. Only Projects has a manifest (unregistered).

**PROPOSED lifecycle (per module):** (1) manifest declares id, version, owned permission keys, owned events, dependencies (module ids); (2) registration is explicit in a provider list (no auto-discovery); registry rejects unknown dependency, duplicate permission key ownership, and permission keys not in the Core catalog; (3) activation per §F; (4) module migrations live with the module but run through the application's single migration path (shared-hosting deploys run one `migrate`); seeders are opt-in and idempotent (Stage 03B precedent); (5) contract versioning: `Contracts/` interfaces are append-only within v1; breaking changes require a new interface, never silent signature change; (6) removal: a module may be disabled platform-wide (kill-switch) without code removal; code removal is a normal staged change. Core never imports a module; modules import Core freely; integrations import only `Contracts/`.

## L. Product architecture (product-alignment stage)

The platform serves three product families — **Personal OS, Organization OS, Specialized Solutions** — from one Core. The canonical inventory lives in `product-and-module-catalog.md`; the binding rules are:

1. **Four layers, strictly ordered by dependency:** (i) Platform Core (this document §§A–K) — product-agnostic; (ii) reusable business modules (`tasks`, `calendar`, `content`, `dam`, `finance`, `crm`, `forms`, `workflows`, …) — own records and contracts, used by several families; (iii) specialized solution modules (`events`, `competitions`, `surveys`, `media-ops`, …) — domain logic composed over reusable modules, never re-implementing them (competition judging lives in `competitions`, the shared question/response engine in `forms`); (iv) solution templates & dashboard compositions — data-only configuration (activation sets, role selections, widget layouts, starter structures) owning no records. Core knows none of the business layers; lower layers never import higher ones; solutions import reusable modules only via `Contracts/`.
2. **One workspace, many solutions:** solutions coexist in a workspace as activation + composition. Records stay single-sourced in their owning module under that workspace; cross-module display uses references and live contract reads (`cross-module-contracts.md`) — no per-solution copies (e.g. a finance record shown on an event dashboard remains a `finance` record, visible only per `finance` permissions).
3. **Independent workspaces for separate boundaries:** different membership, confidentiality, billing, or retention needs ⇒ separate workspace(s). Cross-workspace sharing/transfer is not a v1 capability; the workspace remains the security boundary.
4. **Personal dashboard:** a composition surface aggregating — per request, under each source workspace's own authorization context — authorized summaries from the user's personal and organizational workspaces. Nothing is copied into the personal workspace; membership loss takes effect on the next request; field-level exposure follows source permissions (contracts doc §4).
5. **Portals and public participants:** public-facing surfaces (event pages, survey links, competition entries) operate on module-owned participant identities with capability-scoped contracts, entirely outside workspace membership (contracts doc §5). Integrations act as scoped service identities (contracts doc §6).
6. **Future product areas** (inventory, assets, contracts, correspondence, LMS, courses, commerce, advanced accounting) are catalog ID reservations only — they impose no Core v1 requirements beyond the module lifecycle in §K.

## Explicitly deferred beyond Core v1

Automatic payments/online renewal; per-member permission overrides; temporary/expiring roles; cross-workspace data transfer/sharing; nested departments; a general rules/policy engine; multi-region; MariaDB certification; advanced file retention/legal hold. (See capability matrix for per-area status.)
