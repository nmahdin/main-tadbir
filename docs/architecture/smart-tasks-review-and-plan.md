# تسک‌های رویدادمحور تدبیر — بررسی و طرح اجرا

تاریخ بررسی: 2026-09-29<br>
مبنای بررسی: `ddb954a9146ef9f2aac9936af3b27e70875d967a` روی شاخهٔ `arena/01a0e7dd-main-tadbir`.

**وضعیت: بررسی و طراحی کل سیستم + پیاده‌سازی محدود قاعدهٔ انتشار.** فقط مسیر «ثبت انتشار در تدبیر ← تکمیل تسک انتشار همان محتوا» پیاده شده است؛ بدون URL اجباری، بدون تأیید اضافه و بدون ادعای تحویل خارجی. شروع/خروجی/بازبینی/اصلاح/جلسه/ایده و journal عمومی زیر همچنان طرح توسعه‌اند. migration جدیدی برای این برش اضافه نشده است.

بندهای ۱ و ۲ موجودی/ایرادهای زمان بررسی را ثبت می‌کنند. وضعیت اصلاحات برش انتشار در بند ۶ و راهنمای استقرار آمده است. طرح journal و savepoint بند ۳، قرارداد فعلی انتشار نیست؛ انتشار فعلی با شکست هر اثر، **کل تراکنش منبع و اثرها** را rollback می‌کند. این سند تأیید امنیت سراسری یا آمادگی کل سیستم تسک هوشمند نیست.

## ۲. ایرادهایی که پیش از اتصال رویداد باید رفع شوند

1. `ContentStageTaskSync` با هر sync مشخصات تسک را بازنویسی می‌کند؛ pending_approval کار تولید را review می‌کند، نه completed. هنگام رد، تسک work قبلی را دوباره in_progress می‌کند. `pruneObsoleteTasks` بعضی تسک‌های review را حذف می‌کند. این مسیر نمی‌تواند بدون اصلاح، مبنای حفظ سابقهٔ اصلاح‌ها باشد.
2. AppContext هنگام تعیین مسئول مرحله، علاوه بر sync بک‌اند، مسیر ساخت تسک دیگری دارد. عنوان محتوا و اولین پروژهٔ فهرست هم برای اتصال استفاده شده‌اند؛ این‌ها مرجع معتبر ارتباط نیستند. یک سازندهٔ canonical لازم است.
3. `ContentDetailView.connectedTasks` به تشابه عنوان نیز تکیه دارد. باید فقط ID واقعی محتوا/مرحله ملاک باشد.
4. ثبت خروجی فعلی ابتدا دارایی می‌سازد، خطای اتصال به محتوا را catch و صرفاً log می‌کند، سپس state مرحله را تحویل‌شده نشان می‌دهد. موفقیت ذخیرهٔ دارایی با موفقیت تحویل خروجی یکسان نیست.
5. شروع/ارسال/تأیید/رد در state محلی انجام می‌شود و autosave بعداً می‌نویسد. کلیک یا state خوش‌بینانه رویداد موفق کسب‌وکار نیست. شکست ذخیره باید فرم/خطا را نگه دارد و تسک را تکمیل نکند.
6. انتشار فعلی در `publishContentNow` عمدتاً تغییر state و ساخت URL پیش‌فرض است. در مسیر بررسی‌شده، پاسخ موفق درگاه انتشار خارجی وجود ندارد؛ نباید از این کلیک رویداد «ارسال موفق به کانال» ساخت.
7. permission مسیر عمومی content.update فقط content.edit است. انتشار، review و approve باید جداگانه و روی تغییر واقعی کنترل شوند؛ payload عمومی نباید فرمان اختصاصی را دور بزند.
8. FK فعلی `tasks.content_id`، cascadeOnDelete است. حذف محتوا می‌تواند تسک‌های تاریخی را حذف کند. سیاست حذف باید قبل از تضمین حفظ سابقه، سازگار اصلاح شود.
9. index ترکیبی content/stage/kind یکتا نیست؛ ضمن اینکه برای چند دور اصلاح اصولاً نباید همین سه ستون را بدون شمارهٔ دور، یکتا کرد. دادهٔ قدیمی ممکن است چند تسک مشابه داشته باشد؛ انتخاب دلخواه/حذف آن‌ها قابل قبول نیست.
10. `activity_logs.user_id` دارای cascade است؛ تضمین نگه‌داری تاریخچه بعد از حذف حساب نیازمند بررسی جداگانهٔ FK و ثبت actor snapshot حداقلی است، نه صرفاً افزودن یک متن توضیح.

## ۳. تصمیم‌های طراحی

### تسک عادی و مرتبط

- مسیر POST /tasks و فرم عادی حفظ می‌شوند. تسک عادی هیچ قاعدهٔ اتوماسیون ندارد و رویدادهای منابع آن را تغییر نمی‌دهند.
- صرف project_id یا حتی یک پیوست، تسک را خودکار نمی‌کند.
- تسک مرتبط از فرمان داخل محتوا/جلسه/ایده ساخته می‌شود؛ context مسیر سرور مرجع ارتباط است، نه title یا اولین پروژهٔ فهرست.
- activity از عملیات مشخص صفحه انتخاب/استنتاج می‌شود. در صورت ابهام بین چند خروجی، فقط نام خروجی‌های واقعی به کاربر نشان داده می‌شود، نه نام رویداد و شرط فنی.
- ساخت تکراری همان کار در همان دور، همان اتصال canonical را برمی‌گرداند یا conflict روشن می‌دهد؛ ساخت چند تسک مستقل برای یک محتوا ممنوع نیست، ولی خروجی نباید همه را کورکورانه تکمیل کند.

### توسعهٔ حداقلی داده (پیشنهاد، هنوز migration نیست)

- حفظ `project_id`, `content_id`, `content_stage_id`, `kind` در Task.
- یک FK nullable به `workspace_records` برای جلسه/ایده؛ تطبیق kind در سرویس، نه اعتماد به شناسهٔ خام.
- `origin_task_id` nullable برای زنجیرهٔ اصلاح؛ حذف والد نباید زنجیرهٔ تاریخی را cascade کند.
- metadata اتوماسیون نسخه‌دار و ساختاریافته برای activity/output/delivery iteration؛ فقط سرور آن را می‌نویسد. از تکثیر ID محتوای موجود در چند منبع مستقل اجتناب شود.
- کلید یکتای ساخت برای task/delivery/iteration؛ کلید دور جدید با دور قبلی فرق دارد. task create receipt باید با event receipt تفکیک شود تا چند تسک با یک رویداد، بی‌دلیل از هم جلوگیری نکنند.
- جدول journal رویداد با event_key یکتا، نوع، مرجع منبع، actor، نسخهٔ منبع/خروجی، دادهٔ حداقلی، وضعیت pending/processed/failed/superseded، attempts و زمان پردازش. متن کامل دارایی، رمز یا token در journal ذخیره نشود.
- فعالیت انسانی در همان ActivityLog بماند؛ metadata محدود برای event ID، from/to و output version افزوده شود یا ساختار معادل بدون ایجاد history موازی استفاده شود.
- payload فعلی stages/outputs حفظ شود؛ ایجاد جدول WorkflowStage یا Output موازی در این مرحله توجیه ندارد. نسخهٔ سروری تحویل/بازبینی برای جلوگیری از رد مکرر یک نسخه لازم است.

### تراکنش و رویداد

الگو: اعتبارسنجی و مجوز → قفل/کنترل نسخهٔ منبع → ذخیرهٔ عملیات اصلی و receipt رویداد → پردازش هم‌زمان قواعد در savepoint → تاریخچه و پیشرفت پروژه → commit.

- Listener هم‌زمان Laravel از سرویس مرکزی پردازش استفاده کند؛ وابسته به صف نباشد.
- journal باید با عملیات اصلی commit شود؛ failure اصلی، رویداد و تغییر تسک را rollback کند.
- failure اتوماسیون در savepoint، تغییرات جزئی تسک را rollback می‌کند و receipt شکست را برای تلاش مجدد نگه می‌دارد؛ عملیات اصلیِ موفق بی‌جهت دوباره اجرا نمی‌شود.
- endpoint محدود مدیر برای مشاهدهٔ خطای امن و retry؛ retry عملیات منبع یا ارسال بیرونی را تکرار نمی‌کند.
- در retry، منبع/خروجی، نسخه، actor فعال، مجوز لازم و هدف‌های معتبر دوباره بررسی شوند. رویداد قدیمی نباید تسک تازه‌ساخته یا دور جدید را تکمیل کند.
- کلید یکتا در DB و قفل رکورد اصلی تضمین اصلی‌اند؛ debounce رابط کاربری کافی نیست.
- ترتیب قفل‌ها باید یکسان باشد؛ مدیریت deadlock و retry تراکنش نیز بررسی شود. آزمون SQLite جایگزین همزمانی MySQL نیست.

| ثبت دارایی متنی و اتصال دقیق | تنها کار نگارش متنِ متناظر با همان محتوا/مرحله/خروجی/دور تکمیل شود؛ نه هر تسک مشابه یا هر دارایی |
| ارسال خروجی | پس از اثبات ذخیره و تحویل خروجی‌های لازم، کار تولید completed؛ بازبینی تسک/دور مستقل دارد |

| انتشار | کلیک روی انتشار، پس از ثبت موفق و مجاز سمت سرور، فقط تسک انتشار همان محتوا را کامل می‌کند؛ لینک لازم نیست و تحویل خارجی ادعا نمی‌شود |

وضعیت‌های draft/review/approved در DAM موجودند، اما الزام سراسری تأیید دارایی برای هر خروجی در مسیر فعلی دیده نشد. **تکمیل کار تولید متن با تأیید کیفی یکی نیست**: ثبت یک خروجی متنی معتبر می‌تواند کار تولید را تمام کند؛ مرحلهٔ بازبینی و تسک بازبین مستقل باقی می‌ماند. دارایی rejected/archived، یا دارایی بدون اتصال دقیق، دلیل تکمیل نیست. اگر برای خروجی قاعدهٔ تأیید صریح موجود/تعریف‌شده باشد، شرط تأیید نیز اعمال می‌شود. صرف status ارسالی از کاربر نباید تأیید را جعل کند.

### تغییر دستی

- TaskOperations مرجع مشترک وب/بله و اتوماسیون بماند؛ مسیر خودکار به‌صورت عمومی با source جعلی قابل فراخوانی نباشد.
- تغییر دستی طبق مجوز فعلی مجاز است، اما هرگز محتوا را منتشر، دارایی را تأیید یا صورت‌جلسه را ثبت نمی‌کند.
- در task مرتبط این جدایی به‌وضوح نمایش داده شود. وضعیت منبع واقعی و وضعیت دستی task دو واقعیت متفاوت‌اند.
- پس از ایجاد تسک اصلاحی، بازنویسی تسک تاریخی یا جابه‌جایی ارتباط آن ممنوع/کنترل‌شده باشد؛ اصلاح روی task جدید انجام شود.
- اتوماسیون task، رویداد منبع را دوباره منتشر نمی‌کند؛ حلقهٔ دوطرفه ایجاد نشود.

## ۴. ترتیب پیشنهادی توسعهٔ باقی‌مانده و آزمون

برش انتشار پیش از journal عمومی پیاده شده است؛ مراحل زیر به معنی انجام‌شدن سایر قواعد نیستند.

1. Migration سازگار + SQL phpMyAdmin و preflight؛ رفتار تسک عادی در نبود schema جدید حفظ شود، مسیر هوشمند بدون schema با پیام روشن بسته بماند.
2. هسته journal/processor و کنترل مجوز/قفل/idempotency؛ آزمون unit و feature در DB ایزوله.
3. جایگزینی sync مخرب محتوا و فرمان‌های start/submit/review؛ حذف ایجاد تسک موازی فرانت‌اند و reliance به autosave برای عملیات workflow.
4. اتصال DAM به شناسهٔ دقیق تحویل و نسخه؛ استفادهٔ مجدد از سیاست دسترسی دارایی، نه دورزدن کنترل محرمانگی.
5. اتصال صورت‌جلسه/اقدام و review ایده به عملیات واقعاً معتبر؛ تبدیل چندمرحله‌ای ایده جداگانه اتمیک شود یا رویداد موفق آن فعلاً منتشر نشود.
6. فرم کوچک context-aware در صفحات منبع؛ نمایش پیوند، آخرین علت خودکار، زنجیرهٔ اصلاح و تاریخچه فقط برای کاربر مجاز. فرم عادی بدون فیلد رویداد باقی بماند.
7. تست‌های پذیرش درخواست کاربر به ماتریس آزمون نگاشت شوند: manual unchanged، wrong content/stage/output، duplicate delivery/rejection، rejection round 2، main-operation failure، processor failure/retry، stale event، revoked permission، source deletion، task title collision، و عدم نشت دادهٔ دارایی خصوصی.
8. اجرای دوبارهٔ کل مجموعهٔ قبلی، TypeScript و تست‌های فرانت‌اند، بررسی مرورگر، build تولید و حفظ `frontend/dist` در انتشار.
9. روی کپی MySQL دادهٔ واقعی: آزمون migration، داده‌های قدیمی مشابه، دو درخواست همزمان و بازیابی. استقرار بدون SSH/Cron طبق روال قبلی؛ .env و APP_KEY تولید حفظ شوند.

## ۵. تصمیم قطعی دربارهٔ انتشار

درخواست نهایی کاربر: **«نیازی به لینک واقعی نیست، همان موقع که روی دکمه انتشار کلیک شد تسک انجام شود.»**

قرارداد: **کلیک روی انتشار ← ثبت موفق انتشار در تدبیر ← تکمیل خودکار تسک انتشارِ همان محتوا**. URL مقصد یا تأیید اضافه لازم نیست. خطای اعتبارسنجی/مجوز/ذخیره/پردازش، تکمیل ظاهری تسک ایجاد نمی‌کند. ثبت داخلی تأیید دریافت شبکه/کانال بیرونی نیست؛ این مسیر هیچ درخواست ارسال خارجی اجرا نمی‌کند.

## ۶. پیاده‌سازی فعلی — قاعدهٔ انتشار

### بک‌اند، رویداد و داده

- `ContentPublication`: مرجع فرمان‌های انتشار، لغو، برنامه و ساخت تسک با context واقعی. actor فعال و `content.view` + `content.publish` کنترل می‌شوند. ساخت تسک علاوه بر آن `tasks.create` و `tasks.view` می‌خواهد.
- `ContentPublished(contentId, actorId, eventId)` با listener صریح و هم‌زمان `TaskAutomationProcessor` در AppServiceProvider؛ بدون worker، Cron یا endpoint عمومی برای تزریق رویداد.
- قفل محتوا سپس قفل تسک‌ها؛ اثر تکمیل در `TaskOperations` با ActivityLog و محاسبهٔ موجود پیشرفت پروژه. خطای listener یا نبود آن، ذخیرهٔ منبع و همهٔ اثرها را rollback می‌کند. تکرار فرمان بعد از شکست ممکن است؛ موفقیت دوباره تاریخچه ایجاد نمی‌کند.
- `Content.payload._publication` رسید خصوصی آخرین انتشار با UUID رویداد، actor، شناسهٔ دقیق تسک‌های همان لحظه و processed است. Resource آن را مخفی کرده و فقط `publicationVersion` مشتق‌شده را ارائه می‌کند. رسید، journal عمومی/آرشیو شکست‌ها نیست. دورهای پیشین در ActivityLog و history باقی می‌مانند، نه در این رسید آخرین دور.
- فقط `content_publish` همان `content_id` و تسک قدیمی `content_work` مربوط به مرحلهٔ ذخیره‌شده با `stageKey=publish` هدف‌اند. عنوان مشابه، tag، تسک general، مرحلهٔ تولید یا محتوای دیگر هدف نیست. رویداد قدیمی تسک جدید را تکمیل نمی‌کند.
- تسک انتشار فقط پس از تکمیل همهٔ مراحل جریان ساخته/نمایان می‌شود. تکمیل همان تسک، انتشار محتوا را در همان تراکنش ثبت می‌کند؛ بازگرداندن آن از completed نیز محتوا را به «آماده انتشار» برمی‌گرداند. لغو انتشار از صفحهٔ محتوا، تسک انتشار را به todo بازمی‌گرداند؛ تسک archived دست‌نخورده می‌ماند.
- تغییر publishInfo/ناشر/انتشار از ویرایش عمومی محتوا و تزریق رسید مسدود است؛ autosave حاوی همان مقادیر سازگار است. نسخهٔ قدیمی conflict می‌دهد. ساخت مستقیم `content_publish` در فرم عمومی و تغییر اتصال این kind در update عمومی مسدود است. بازطراحی کامل حفاظت مراحل قدیمی خارج از این برش است.
- `ContentStageTaskSync` در مسیر محدود انتشار تسک تکمیل‌شده/بایگانی‌شده را باز نمی‌کند؛ prune تسک completed/archived را حذف نمی‌کند. review مرحلهٔ انتشار هنگام skip حفظ می‌شود. **منطق مخرب رد/بازبینی سایر مراحل هنوز اصلاح نشده است.**
- هیچ جدول، مدل دامنه یا migration جدید اضافه نشده؛ از Content/Task/ActivityLog موجود استفاده شده است.

### فرانت‌اند

- API-first در AppContext: state محتوا/تسک، پیام موفقیت و celebration فقط پس از پاسخ موفق سرور؛ pending و جلوگیری از کلیک تکراری؛ URL و آمار مصنوعی حذف شده‌اند.
- در 409، اطلاعات محتوا برای تلاش **بعدی و صریح** کاربر بازخوانی می‌شود؛ فرمان روی نسخهٔ تازه خودکار تکرار نمی‌شود. شکست refresh خطای اصلی را نمی‌پوشاند.
- میز انتشار ابتدا برنامه را await می‌کند، سپس نسخهٔ برگشتی را برای انتشار یا ساخت تسک می‌فرستد. شکست ذخیره/انتشار فرم را نمی‌بندد. برنامه‌ریزی به معنی اجرای خودکار در ساعت تعیین‌شده نیست؛ Cron فرض نشده است.
- ارتباط تسک‌های نمای محتوا با `contentId` واقعی است؛ جزئیات تسک انتشار علت/تاریخچه و لینک منبع با gate `content.view` دارد. فرم عادی فیلد فنی رویداد/نسخه نگرفته است.
- autosave عمومی ۵۰۰ میلی‌ثانیه‌ای و سایر عملیات خوش‌بینانهٔ قدیمی هنوز وجود دارند؛ این برش بازنویسی کامل workflow نیست.

### قرارداد، فایل‌ها، تست و استقرار

قرارداد چهار API، فهرست فایل‌های تغییرکرده، نتیجهٔ آزمون‌های نهایی و دستورالعمل بدون SSH/Cron در [راهنمای برش انتشار](../deployment/smart-tasks-publication.md) آمده است. آزمون مرورگر واقعی، MySQL/MariaDB، همزمانی چندپردازشی و هاست/بله انجام نشده‌اند؛ تست Node helper و SQLite جایگزین آن‌ها نیستند.

### باقی‌مانده‌ها

journal عمومی بادوام و مشاهده/retry مستقل خطای اتوماسیون؛ قواعد متن/خروجی/شروع/تأیید/رد و زنجیرهٔ اصلاح چنددوره‌ای؛ اتصال دقیق صورت‌جلسه و بررسی ایده؛ اصلاح FKهای cascade برای حفظ تاریخچه هنگام حذف؛ حذف مسیرهای موازی و optimistic سایر مراحل؛ ACL سراسری و آزمون واقعی همزمانی. هیچ‌یک قابلیت تکمیل‌شده یا تست پاس‌شده گزارش نمی‌شوند.
