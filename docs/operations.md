# راهنمای عملیاتی تدبیر — پیش‌نویس مشروط به تأیید محیط

این سند روش پیشنهادی قابل تطبیق با هاست **بدون SSH و Cron** است، نه گزارش اجرای backup/restore یا استقرار. gate فازهای قبلی طبق [ممیزی فاز چهارم](phase-4-audit.md) هنوز باز است. worker، Redis یا سرویس پایش اضافه نشده است. فقط برای Outbox بله یک tick محدود و secret-based از قبل وجود دارد و اکنون schedule داخلی نیز ثبت شده؛ فعال‌بودن هیچ‌کدام روی هاست از مخزن قابل اثبات نیست.

## ۱. مسئولیت و تصمیم‌های باز

| موضوع | وضعیت / تصمیم لازم پیش از انتشار |
|---|---|
| مسئول release و rollback | مالک سامانه باید یک مسئول و جانشین مشخص کند؛ هنوز نام/تأیید نداریم. |
| اجرای backup | قابلیت کنترل‌پنل و مسئول اجرای آن باید با پشتیبانی هاست تأیید شود. نبود Cron به معنی وجود backup خودکار نیست. |
| محل نگهداری | پیشنهاد: فضای رمزگذاری‌شدهٔ خصوصی خارج webroot و یک کپی خارج همان حساب/سرور؛ سرویس یا مقصد واقعی هنوز تعیین نشده است. |
| دوره و retention | با حجم/حساسیت داده و RPO مصوب تعیین شود. پیشنهاد اولیه برای بررسی: روزانه، پیش از هر release و تغییر schema؛ روزانه ۷ نسخه و هفتگی ۴ نسخه. **این سیاست هنوز فعال/مصوب نیست.** |
| RPO/RTO | حداکثر دادهٔ قابل‌از‌دست‌رفتن و زمان بازیابی باید توسط مالک تعیین و با restore drill سنجیده شوند؛ عدد تضمینی نداریم. |
| وضعیت backup فعلی | از مخزن قابل اثبات نیست. رسید backup، حجم، checksum، زمان و نتیجهٔ restore آزمایشی باید در محل خصوصی ثبت شود. |

## ۲. پیش‌نیازهای سرور و محیط

- نسخهٔ PHP و extensionها مطابق `backend/composer.lock` و `composer check-platform-reqs --no-dev` روی محیط سازگار با هاست بررسی شوند؛ composer.json شرط PHP ^8.3 و Laravel ^13.17 دارد. صرف انتخاب نسخه در پنل کافی نیست؛ PDO دیتابیس، fileinfo، mbstring و امکانات موردنیاز dependencyها باید تأیید شوند.
- DocumentRoot دامنهٔ API فقط `backend/public` باشد؛ `.env`، vendor، دیتابیس، backup و log از وب قابل دریافت نباشند. پنل از **کل** `frontend/dist` و `.htaccess` آن سرو شود؛ rewrite مستقیم `/tasks/{id}` نیازمند پشتیبانی Apache/AllowOverride است.
- HTTPS هر دو دامنه و ارتباط خروجی HTTPS با بله در صورت فعال‌بودن بات، محدودیت upload/request/memory/timeout و ظرفیت دیسک کنترل شود. مجوز نوشتن فقط برای مسیرهای موردنیاز مانند storage و bootstrap/cache، نه 0777 عمومی.
- `backend/.env.example` تولید، `.env.local.example` SQLite محلی و `frontend/.env.production.example` تنظیمات عمومی build هستند. نمونه را روی `.env` موجود کپی نکنید. APP_KEY و رمز DB و رمزهای seed خصوصی‌اند؛ هیچ secret وارد VITE_*، Git یا log نشود.
- env تولید: APP_ENV=production، APP_DEBUG=false، APP_URL دامنهٔ API، DB_* واقعی، تنظیمات HTTPS/domain/Sanctum طبق [environment.md](environment.md). config/cors.php به origin پنل محدود است؛ مقدار فرضی CORS در env اضافه نکنید.
- QUEUE_CONNECTION=sync، CACHE_STORE=file و SESSION_DRIVER=file در نمونه‌اند و queue worker عمومی نداریم. `routes/console.php` فقط `bale:tick` را هر دقیقه ثبت می‌کند. اجرای schedule روی هاست یا runner HTTPS خارجی باید واقعاً پیکربندی و heartbeat آن مشاهده شود؛ بدون runner تأییدشده، retry پیام‌های بله تضمین‌شده نیست ([راهنمای بله](bale-bot.md)).

## ۳. آماده‌سازی release خارج هاست

این فرمان‌ها فقط روی دستگاه توسعه/CI دارای Node، PHP و Composer سازگار اجرا می‌شوند؛ روی هاست فاقد CLI دستور اجرایی قطعی نیستند:

```bash
cd frontend
npm ci
npm run lint
npm test
# پس از تنظیم فایل خصوصی .env.production از روی مثال عمومی
npm run build
```

```bash
cd backend
composer install --no-dev --prefer-dist --optimize-autoloader
composer check-platform-reqs --no-dev
```

تست‌های بک‌اند باید **قبل از حذف dev dependencyها، در checkout آزمایشی جدا** اجرا شوند. دستور `composer setup` نصب موجود را هدف نگیرد؛ شامل key:generate است. هیچ‌گاه برای رفع خطای release کلید موجود را دوباره تولید نکنید.

بستهٔ انتشار شامل backend، vendor سازگار، تمام dist و فایل‌های rewrite باشد؛ نه node_modules، `.env` واقعی، دیتابیس آزمایشی و گزارش آزمون. dist در Git طبق نیاز هاست باقی می‌ماند. build این ممیزی خارج مخزن و فقط برای اندازه‌گیری بود؛ artifact منتشرشده را عوض نکرد.

## ۴. backup هماهنگ پیش از تغییر

1. با ابزار کنترل‌پنل/پشتیبانی هاست، نوشتن در برنامه و ورودی‌هایی که داده تغییر می‌دهند (از جمله webhook) موقتاً متوقف شود. نداشتن SSH را با ساخت route عمومی اجرای artisan دور نزنید.
2. export سازگار DB با ابزار هاست و گزینه‌های لازم charset/collation/trigger/FK، همراه فایل‌های خصوصی `storage/app/private` و عمومی `storage/app/public` انجام شود. برای SQLite زنده کپی سادهٔ فایل در حین نوشتن کافی نیست؛ از روش backup سازگار یا توقف کامل نویسنده استفاده شود.
3. نسخهٔ دقیق کد/vendor/dist و `.env`/APP_KEY موجود جداگانه و رمزگذاری‌شده نگهداری شوند. از cache/session به‌عنوان دادهٔ مرجع حساب‌ها استفاده نشود. DB تنها، برای بازیابی فایل‌ها یا مقدارهای رمزگذاری‌شدهٔ بات کافی نیست.
4. زمان snapshot، commit release، schema/migrations، فهرست/اندازه/checksum فایل‌ها، مالک backup و محل امن ثبت شود؛ secret یا متن اسناد در فهرست عمومی قرار نگیرد. دانلودناپذیری مسیر backup از وب بررسی شود.
5. پیش از بازکردن نوشتن، صحت دریافت و فضای کپی دوم بررسی شود. backup ناقص یا بدون آزمایش بازیابی، تضمین بازیابی محسوب نمی‌شود.

## ۵. migration و deploy روی هاست واقعی

- ابتدا روی **کپی جداگانهٔ DB و فایل‌ها** با PHP و موتور DB سازگار تست شود. SQLite/WASM موجود جای آزمون MySQL نیست. JSON، collation، FK، حفظ شناسه‌ها، قفل DDL و زمان اجرا بررسی شوند؛ SQL جایگزین حدسی ننویسید.
- استثنای مهم release مبنا `b8333a44`: ستون ایمیل و جدول reset از مایگریشن‌های **پایه** حذف شده‌اند. migrate عادی روی DB قدیمی آن‌ها را حذف نمی‌کند. این release برای schema تازه/بازسازی‌شده است؛ برنامهٔ ارتقای درجا از DB قدیمی ارائه نشده است. [username-accounts.md](username-accounts.md) را بررسی کنید.
- `migrate:fresh --seed` فقط برای دیتابیس صریحاً قابل حذف و بعد از تصمیم مالک است؛ نه بخشی از deploy معمول. همهٔ داده‌ها حذف می‌شوند و سید فقط سه حساب اولیه و نقش/مجوز پایه را برمی‌گرداند. درخواست قبلی fresh، مجوز تکرار آن در هر انتشار نیست.
- اگر کنترل‌پنل task امن CLI دارد یا پشتیبانی هاست اجرای آن را انجام می‌دهد، دستورات لازم زیر **پس از بررسی سازگاری migration** از همان backend و env واقعی اجرا می‌شوند؛ در غیر این صورت روش نصب و انتقال DB باید جداگانه تأیید شود، نه با endpoint وب یا overwrite دیتابیس زنده:

```bash
php artisan migrate --force
php artisan config:clear
php artisan route:clear
php artisan view:clear
# فقط پس از تأیید env واقعی همان هاست:
php artisan config:cache
```

این فهرست دستورالعمل مشروط است و در این نوبت اجرا نشده است. اگر هاست CLI ندارد، ساخت جدول نشست کوتاه‌عمر Mini App فقط با backup، بررسی FK/type و فایل `docs/deployment/bale-panel-session.mysql.sql` انجام شود؛ SQL را پس از migrate دوباره اجرا نکنید. config cache دستگاه توسعه به هاست منتقل نشود. application cache، rate limiter، session و کلیدهای dedupe را بدون بررسی پاک نکنید. بازنشانی OPcache یا PHP از کنترل‌پنل/پشتیبانی انجام شود؛ endpoint عمومی phpinfo/reset نسازید.

تعویض هماهنگ backend و کل dist در بازهٔ توقف انجام شود. اگر پنل امکان تعویض اتمیک پوشه دارد از آن استفاده کنید؛ امکان آن هنوز تأیید نشده است. یک manifest **خصوصی** شامل commit هر دو بخش، checksum artifact و زمان انتشار نگهداری کنید. API فعلی health فقط v1 قرارداد را گزارش می‌کند و شناسهٔ release خودکار ندارد؛ در تطبیق نسخه، به v1 اکتفا نکنید.

## ۶. بررسی بعد از deploy

- GET `/api/v1/health` و `/api/v1/health/db`: پاسخ سلامت یا 503 امن؛ این‌ها proof صحت schema، ذخیرهٔ فایل، queue یا مجوز نیستند. secret/query واقعی برای health لازم نیست. همان دو پاسخ روی داشبورد پنل در کارت «وضعیت سامانه و بک‌اند» برای همهٔ کاربران واردشده نمایش داده می‌شوند؛ فقط با دکمهٔ «بررسی مجدد» (بدون polling) و بدون نمایش متن خام سرور. این کارت جای پایش سرور، صف، storage، backup یا نسخهٔ release را نمی‌گیرد.
- GET `/` روی دامنهٔ API (`https://api-tadbir.morvarid-daron.ir/`): صفحهٔ مستقل «وضعیت بک‌اند تدبیر» که فقط API، دیتابیس، زمان سرور (وقت تهران) و نسخهٔ API را از همان دو endpoint عمومی بالا می‌خواند؛ وابسته به frontend نیست و برای نمایش آن لازم نیست `dist` منتشر شود. صفحه نشست/کوکی/query ندارد، polling ندارد (فقط هنگام باز شدن و دکمهٔ «بررسی مجدد») و تنظیمات، نسخهٔ PHP/Laravel یا متن خطا نشان نمی‌دهد. پایش خودکار (uptime monitor) همچنان باید از `/up` یا `/api/v1/health` انجام شود، نه از این صفحهٔ HTML. اگر صفحهٔ سفید/204 دیدید، نسخهٔ قدیمی `routes/web.php` روی هاست مانده یا `bootstrap/cache/routes*.php` باید حذف شود.
- اگر ربات بله فعال است، Webhook واقعی، اتصال یک حساب آزمایشی، ورود یک‌بارمصرف Mini App (موفقیت بار اول و رد بار دوم)، cleanup منوی callback، اعلان آزمایشی، runner و heartbeat اخیر بررسی شوند. روی هاست دارای Cron، scheduler استاندارد Laravel؛ روی هاست بدون Cron، POST محدود و bearer-protected شرح‌داده‌شده در `docs/bale-bot.md` لازم است. secret runner نباید در URL یا log باشد.
- ورود/خروج با حساب مجاز و غیرمجاز، session و CSRF و CORS دو دامنه، رد شناسهٔ غیرمجاز، پیوند مستقیم و refresh، ساخت/ویرایش و حفظ فرم در 422، archive/restore، approval conflict، unread و pagination بررسی شوند.
- upload/preview/download مجاز و غیرمجاز فایل خصوصی و رد نوع غیرمجاز، همراه تست عدم دانلود `.env`/log/backup از DocumentRoot کنترل شوند. سند یا فایل واقعی محرمانه برای smoke استفاده نشود.
- خروجی backend در `storage/logs/laravel.log` طبق تنظیم واقعی بررسی شود؛ نمونهٔ فعلی single است و rotation خودکار روزانه تضمین ندارد. مدیریت اندازه/retention با هاست هماهنگ شود. body درخواست، Authorization، cookie، رمز، URL حامل secret و متن اسناد وارد گزارش پشتیبانی نشود.
- pipeline correlation ID عمومی و پایش frontend هنوز وجود ندارد. تا تکمیل آن، زمان دقیق/مسیر بدون دادهٔ حساس/status و release خصوصی برای بررسی جمع‌آوری شود؛ raw console یا log بدون بازبینی به بیرون ارسال نشود.

## ۷. restore drill و rollback

**این تمرین در این نوبت انجام نشده است؛ شرط آمادگی عملیاتی باقی می‌ماند.** مسئول باید در محیطی جدا با DB، storage و دامنهٔ مستقل تمرین کند:

1. آخرین backup سازگار را رمزگشایی و checksum آن را تأیید کند؛ سپس DB و فایل‌ها را به مقصد جدا restore کند و کد/vendor/dist متناظر را قرار دهد.
2. برای دادهٔ رمزگذاری‌شده کلید backup حفظ شود، ولی اتصال DB و URLها فقط آزمایشی باشند. دسترسی خروجی شبکه به سرویس‌های واقعی/بله مسدود و runner/ارسال واقعی غیرفعال شود؛ secret یا webhook تولید بازثبت نشود.
3. تعداد رکوردها و FKهای اصلی، hash فایل‌ها، شناسه/روابط، ورود، مجوز منفی، خواندن فایل خصوصی و نمایش workflow را با snapshot مقایسه کند. هیچ شمارش ساختگی به‌عنوان تعداد تولید گزارش نشود.
4. زمان واقعی restore و مقدار دادهٔ ازدست‌رفته را نسبت به RTO/RPO مصوب ثبت کند؛ خطا، مسئول و زمان backup بعدی مشخص باشند. سپس دادهٔ آزمایشی محرمانه طبق سیاست نگهداری پاک شود.

Rollback: ابتدا نویسنده‌ها را متوقف و از وضعیت شکست‌خورده برای تحلیل backup امن تهیه کنید. اگر schema با کد قبلی سازگار است، فقط کد و dist هماهنگ قبلی و cache محیط همان هاست برگردند. اگر سازگار نیست، DB/فایل/کلید/کد باید از snapshot هماهنگ restore شوند؛ ازبین‌رفتن تغییرات بعد از snapshot نیازمند تأیید مالک است. `migrate:rollback` معادل بازیابی مطمئن نیست؛ بعضی downهای مخزن عمداً غیرتخریبی‌اند و حذف دادهٔ ایمیل/بازسازی DB قابل معکوس‌کردن خودکار نیست.

## مرز این راهنما

هاست، MySQL، OPcache، backup خودکار، مقصد نگهداری و RTO/RPO هنوز تأیید نشده‌اند. دستور تازهٔ deploy خودکار، سرویس backup، health نسخه‌دار جدید یا قابلیت monitoring پیاده نشده است. این سند باید با کنترل‌پنل واقعی و مسئول مشخص تکمیل و پس از یک restore موفق تأیید شود؛ به‌تنهایی فاز سوم را Done نمی‌کند.
