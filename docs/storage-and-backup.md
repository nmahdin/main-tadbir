# محل ذخیره‌سازی فایل‌ها و پشتیبان‌گیری دیتابیس

این سند پاسخ سه پرسش عملیاتی است: فایل‌های آپلودشده کجا ذخیره می‌شوند، چطور محل
ذخیره را به پوشه‌ای بیرون از نرم‌افزار منتقل کنیم که با آپدیت از دست نرود، و
چطور از دیتابیس پشتیبان بگیریم و در صورت نیاز به دادهٔ قبلی برگردیم.

> خلاصهٔ یک‌خطی: **پوشهٔ نرم‌افزار موقتی است، پوشهٔ داده ماندنی.** کد را می‌توان
> هر بار جایگزین کرد؛ فایل‌ها و دیتابیس باید بیرون از آن باشند.

## ۱. فایل‌های آپلودشده الان کجا هستند؟

| کاربرد | دیسک | ریشهٔ پیش‌فرض | در استقرار توصیه‌شده |
| --- | --- | --- | --- |
| DAM (فایل، متن، پیوست گفتگو) | `local` | `backend/storage/app/private` | بیرون از نرم‌افزار |
| فایل‌های عمومی (در صورت استفاده) | `public` | `backend/storage/app/public` | خالی است و استفاده نمی‌شود |
| ذخیره‌سازی ابری | `s3` | — | پیکربندی نشده |

- انتخاب دیسک پیش‌فرض با `FILESYSTEM_DISK` انجام می‌شود (پیش‌فرض `local`).
- ریشهٔ دیسک `local` با متغیر جدید `TADBIR_FILES_ROOT` تعیین می‌شود. اگر خالی
  باشد، همان `backend/storage/app/private` قبلی است؛ یعنی **نصب فعلی بدون هیچ
  تغییری کار می‌کند**.
- هر رکورد DAM دیسک خودش را در ستون `dam_files.storage_disk` نگه می‌دارد؛ پس
  تغییر دیسک، رکوردهای قدیمی را خراب نمی‌کند و هر فایل از همان جایی که هست
  خوانده می‌شود.
- مسیر واقعی هر فایل برای مدیر کل سامانه در صفحهٔ DAM زیر «آدرس فایل روی هاست»
  نمایش داده می‌شود؛ همین مسیر باید در پشتیبان‌گیری فایل استفاده شود.

## ۲. انتقال ریشهٔ فایل‌ها به پوشه‌ای که با آپدیت عوض نمی‌شود

### گام ۱ — ساخت پوشهٔ داده روی هاست

پوشه‌ای بیرون از پوشهٔ نرم‌افزار بسازید، مثلاً:

```
/home/<user>/tadbir-data/files
/home/<user>/tadbir-data/backups
```

سطح دسترسی قابل نوشتن برای کاربر PHP (روی هاست اشتراکی معمولاً `0755` کافی است؛
اگر سخت‌گیرانه است `0770` و مالک/گروه همان کاربر PHP).

### گام ۲ — تنظیم `.env`

```dotenv
TADBIR_FILES_ROOT=/home/<user>/tadbir-data/files
TADBIR_FILES_LEGACY_ROOT=/home/<user>/backend/storage/app/private
TADBIR_BACKUP_ROOT=/home/<user>/tadbir-data/backups
TADBIR_BACKUP_KEEP=7
```

`.env` واقعی هاست را جایگزین نکنید؛ فقط این خطوط را اضافه کنید. پس از تغییر
`.env`، کش تنظیمات (در صورت وجود `bootstrap/cache/config.php`) و OPcache را پاک
کنید.

### گام ۳ — انتقال فایل‌های موجود

```bash
cd backend
php artisan tadbir:files-relocate             # گزارش: چند فایل، چند مگابایت
php artisan tadbir:files-relocate --apply     # انتقال واقعی (روی یک دیسک: rename)
```

- اگر دو مسیر روی یک دیسک باشند، `rename` انجام می‌شود (سریع، بدون فضای دوبرابر).
- اگر روی دو دیسک باشند، کپی می‌شود؛ پس از تأیید می‌توانید با
  `--apply --prune-source` فایل‌های مبدأ را پاک کنید.
- دستور تکرارپذیر است: فایل‌هایی که مقصد دارند، رد می‌شوند. اجرای محدود
  `--limit=500` برای پوشه‌های بزرگ.

**روی هاست بدون SSH:** در `.env` مقدار `TADBIR_MAINTENANCE_SECRET` را به یک
رشتهٔ تصادفی ≥۳۲ کاراکتری تنظیم کنید و از مسیر تعمیر استفاده کنید:

```bash
curl -X POST https://api-<domain>/api/v1/maintenance/files-relocate \
  -H "Authorization: Bearer <secret>" -H "Content-Type: application/json" \
  -d '{"apply":false}'                       # گزارش
curl -X POST https://api-<domain>/api/v1/maintenance/files-relocate \
  -H "Authorization: Bearer <secret>" -H "Content-Type: application/json" \
  -d '{"apply":true,"limit":200}'            # انتقال محدود و تکرارپذیر
```

### گام ۴ — تأیید

1. در DAM یک فایل قدیمی را باز کنید (پیش‌نمایش و دانلود).
2. یک فایل جدید آپلود کنید و در File Manager حضور آن را زیر
   `.../tadbir-data/files/dam/...` ببینید.
3. گزارش `POST maintenance/files-relocate {"apply":false}` باید `pending: 0`
   بدهد.
4. تا زمانی که همه‌چیز تأیید نشده، پوشهٔ قدیمی را پاک نکنید.

### نکات

- فایل‌های فاقد بایت واقعی (پیوست‌های legacy که فقط metadata داشتند) منتقل
  نمی‌شوند و لازم هم نیست.
- پوشهٔ `storage/framework/*` (کش، نشست، ویو) بخشی از دادهٔ کاربر نیست و با هر
  انتشار می‌تواند پاک شود.
- انتقال فایل، رکوردهای دیتابیس را تغییر نمی‌دهد؛ مسیر داخل رکورد نسبی است.

## ۳. پشتیبان‌گیری دیتابیس

### چه چیزی باید پشتیبان گرفته شود؟

| مورد | چرا | ابزار |
| --- | --- | --- |
| دیتابیس (جدول‌ها) | همهٔ محتوا، وظایف، کاربران، جریان تولید | `php artisan tadbir:backup` |
| فایل‌های آپلودشده | فایل‌های DAM بیرون از DB هستند | `--with-files` (tar.gz) یا پشتیبان هاست |
| `.env` و `APP_KEY` | بدون `APP_KEY` دادهٔ رمزنگاری‌شده خوانده نمی‌شود | کپی دستی امن، بیرون از وب |
| `frontend/dist` | artifact انتشار | در Git است؛ پشتیبان لازم ندارد |

`APP_KEY` را هرگز تغییر ندهید و همیشه همراه پشتیبان نگه دارید؛ دیتابیس بدون
کلید همان نصب، قابل بازیابی نیست.

### ساخت پشتیبان

```bash
cd backend
php artisan tadbir:backup                            # پشتیبان دیتابیس
php artisan tadbir:backup --label=before-update      # برچسب‌دار، قبل از آپدیت
php artisan tadbir:backup --with-files               # همراه آرشیو فایل‌ها (tar)
php artisan tadbir:backup --list                     # فهرست پشتیبان‌ها + تأیید هش
php artisan tadbir:backup --keep=14                  # تعداد نسخهٔ نگه‌داشته‌شده
```

خروجی در `<TADBIR_BACKUP_ROOT>/db/` نوشته می‌شود:

```
db-20261012-031000-before-update.sql.gz     ← خود دامپ (gzip)
db-20261012-031000-before-update.json       ← manifest: جدول‌ها، ردیف‌ها، هش SHA-256،
                                              آخرین migrationها، مسیر فایل‌ها
```

- دامپ با همان اتصال PDO ساخته می‌شود؛ **نیازی به `mysqldump` یا SSH نیست**.
- هر جدول `DROP TABLE IF EXISTS` + `CREATE TABLE` + `INSERT` دارد و کلیدهای
  خارجی هنگام بازگردانی خاموش می‌شوند؛ پس بازگردانی روی همان نصب تکرارپذیر است.
- دادهٔ فارسی و بایت‌های خاص با `X'..'` نوشته می‌شوند تا charset اتصال خرابشان نکند.
- manifest به شما می‌گوید پشتیبان روی کدام نسخهٔ schema گرفته شده است.
- نگه‌داشت نسخه‌ها با `TADBIR_BACKUP_KEEP` (پیش‌فرض ۷) کنترل می‌شود؛ قدیمی‌ترها
  با هر پشتیبان جدید حذف می‌شوند.
- اگر cron/scheduler فعال باشد، هر شب ساعت ۰۳:۱۰ یک پشتیبان `scheduled` ساخته
  می‌شود. در غیر آن صورت از مسیر تعمیر استفاده کنید:

```bash
curl -X POST https://api-<domain>/api/v1/maintenance/backup \
  -H "Authorization: Bearer <secret>" -H "Content-Type: application/json" \
  -d '{"label":"before-update","with_files":false}'
```

### بازگردانی

```bash
php artisan tadbir:restore --list                       # انتخاب فایل
php artisan tadbir:restore db-20261011-031000.sql.gz --confirm=db-20261011-031000.sql.gz
```

- بدون `--confirm` برابر نام فایل، **هیچ نوشتنی انجام نمی‌شود**.
- پیش از بازگردانی، خودکار یک پشتیبان ایمنی با برچسب `pre-restore` گرفته می‌شود.
- هش فایل با manifest مقایسه می‌شود؛ فایل دست‌کاری‌شده رد می‌شود.
- بازگردانی روی درایور متفاوت (مثلاً پشتیبان MySQL روی SQLite) پذیرفته نمی‌شود.
- بازگردانی عمداً فقط در CLI است، نه یک دکمهٔ وب: عملیاتی برگشت‌ناپذیر است و
  باید با دسترسی سرور انجام شود.
- پس از بازگردانی، کش مسیرها/تنظیمات و OPcache را پاک کنید و ورود/فهرست محتوا
  را یک بار بررسی کنید.

### نگه‌داشتن دادهٔ قبلی در آپدیت (بدون از دست رفتن جدول‌ها)

1. **پیش از هر آپدیت** `php artisan tadbir:backup --label=before-update` بزنید و
   `--list` را برای تأیید هش ببینید.
2. آپدیت‌ها باید **افزایشی** باشند: ستون/جدول جدید اضافه می‌شود و ستون یا جدول
   موجود حذف نمی‌شود. این پروژه هم همین سیاست را دارد: هیچ migration ای جدول
   کاربران را خالی نمی‌کند و جدول `migrations` نشان می‌دهد کدام تغییرات اجرا شده‌اند.
3. روی **کپی** دیتابیس تست کنید: دیتابیس را در همان هاست با نام دیگر بسازید،
   پشتیبان را در آن بازیابی کنید و migrationها را همان‌جا اجرا کنید.
4. migration را با `php artisan migrate --force` اجرا کنید. اگر شکست خورد،
   دادهٔ قبلی سر جایش است (migration هر جدول را جدا و در تراکنش تغییر می‌دهد).
5. اگر بازگشت لازم شد: `php artisan tadbir:restore <backup> --confirm=<backup>`
   و بعد autoload/کد نسخهٔ قبلی را برگردانید (کد و دیتابیس هم‌زمان).
6. نسخهٔ دیتابیس پشتیبان را جدا نگه دارید: پس از بازگردانی، نسخهٔ جدید migration
   ها ممکن است لازم باشد دوباره اجرا شوند.

### چه چیزی پشتیبان‌گیری نمی‌شود (شفاف)

- انتقال خودکار پشتیبان به فضای ابری/دیسک دوم پیاده نشده است؛ برای این کار
  پشتیبان را با `rsync`/ابزار هاست کپی کنید.
- بازیابی نقطه‌ای (point-in-time) و باینری‌لاگ MySQL پشتیبانی نمی‌شود.
- دکمهٔ پشتیبان‌گیری در پنل مدیریت وجود ندارد؛ ابزار CLI و مسیر تعمیر است.
- پشتیبان‌گیری از دیتابیس، فایل‌ها را شامل نمی‌شود مگر با `--with-files`.

## ۴. تازه‌سازی وضعیت مشتق محتوا (بدون cron)

وضعیت «در تأخیر» و «مهلت مرحله» از دادهٔ واقعی سرور ساخته می‌شوند و در فهرست
محتوا، جزئیات پرونده و گزارش‌ها به‌صورت محدود (۵۰ پرونده) تازه می‌شوند. روی
هاستی که cron ندارد، می‌توانید صریحاً هم اجرا کنید:

```bash
php artisan content:overdue-notifications        # یادآوری‌ها + تازه‌سازی وضعیت
php artisan contents:refresh-deadline-status     # پرونده‌های بدون مهلت مرحله
```

```bash
curl -X POST https://api-<domain>/api/v1/maintenance/refresh-status \
  -H "Authorization: Bearer <secret>" -H "Content-Type: application/json" \
  -d '{"limit":500}'
```

و برای دیدن اینکه چند پرونده از مهلت گذشته و چند پرونده هرگز هم‌گام نشده است:

```bash
curl https://api-<domain>/api/v1/maintenance/status -H "Authorization: Bearer <secret>"
```

## ۵. چک‌لیست پیش از آپدیت

1. `php artisan tadbir:backup --label=before-update` و تأیید `--list`.
2. کپی امن از `.env` (با `APP_KEY`).
3. پشتیبان فایل‌ها (اگر `TADBIR_FILES_ROOT` بیرون است، `tar` از همان پوشه).
4. اجرا/توقف موقت نوشتن کاربران و آگاهی دادن به آن‌ها.
5. جایگزینی کد + `frontend/dist` هم‌زمان.
6. `php artisan migrate --force` و پاک‌کردن کش مسیرها/تنظیمات.
7. بررسی: ورود، فهرست محتوا، جزئیات یک پرونده، یک پیش‌نمایش فایل، یک آپلود.
