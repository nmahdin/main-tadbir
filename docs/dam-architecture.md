# مدیریت دارایی‌های دیجیتال (DAM)

## مرحلهٔ ۱ — بررسی پروژه و طراحی سازگار

### فناوری‌ها و قراردادهای موجود
- **Backend:** Laravel 13، PHP حداقل 8.3، پایگاه دادهٔ پیش‌فرض SQLite در محیط توسعه، API نسخهٔ `/api/v1` و احراز هویت Sanctum. مجوزها از Role/Permissionهای موجود و متدهای `User::hasPermission` / `hasAnyPermission` می‌آیند.
- **Frontend:** React 19 + TypeScript + Vite، Tailwind CSS 4، رابط فارسی/RTL و فونت Vazirmatn. زبان بصری سامانه بر پایهٔ پنل‌های سفید، حاشیه‌های slate، رنگ indigo، گوشه‌های گرد و سایه‌های ملایم است.
- **پیشینهٔ DAM:** در مخزن، مدل‌ها، مهاجرت‌ها، `DamService` و API اولیه وجود داشت؛ اما صفحهٔ اصلی و برخی modalهای قدیمی به `AppContext`/`localStorage` تکیه می‌کردند و URLهای موقت مرورگر یا metadata را به‌جای ذخیرهٔ فایل واقعی نشان می‌دادند. صفحهٔ پروژه و وظیفه نمونه‌ای از استفاده از `DamLibrary` داشتند.
- **ماژول‌های مجاور:** پروژه، وظیفه، دپارتمان و نقش‌ها مدل‌ها و مجوزهای مستقل خود را دارند. پیوست وظیفه و پیوست‌های گفتگو/جلسه در حال حاضر هنوز مسیرهای legacy دارند.

### معماری سازگار
1. دارایی file/content در `dam_assets` یک شناسنامه و شناسهٔ مستقل دارد. مشخصات نسخهٔ فایل در `dam_files` و محتوای متنی در `dam_content_items` جدا ذخیره می‌شوند.
2. فایل‌ها با disk خصوصی Laravel (`local`، در استقرار باید خارج از web root باشد) ذخیره می‌شوند. برنامه از Storage facade عبور می‌کند تا disk قابل‌تعویض بماند؛ اتصال MEGA فعال یا آزمایش‌شده فرض نشده است.
3. نسخه‌ها append-only هستند؛ فایل‌های نسخهٔ قبلی حذف نمی‌شوند. بازیابی نسخه، نسخهٔ جدید و رویداد تاریخچه می‌سازد.
4. روابط پروژه/وظیفه/دپارتمان در `dam_relations` ثبت می‌شوند و فایل کپی نمی‌شود. درگاه مشترک `DamLibrary` context می‌گیرد تا روابط صفحهٔ فراخواننده از پیش اعمال شوند.
5. به‌جای ادغام مخرب `DomainRecord` یا پیوست‌های legacy، مسیر جدید و واقعی `/api/v1/dam/library` استفاده می‌شود. دادهٔ قدیمی‌ای که بایت فایل ندارد به‌عنوان فایل معتبر مهاجرت داده نمی‌شود.
6. محرمانگی سه‌سطحی از مجوز نقش جداست. برای دارایی confidential، علاوه بر مجوز عملیاتی، مالک یا مدیر بودن بررسی می‌شود؛ download و preview فقط از endpoint مجاز انجام می‌شود.

### ریسک‌ها و تصمیم‌های باز
- SQLite برای توسعه مناسب است؛ در استقرار تولیدی باید سیاست backup، حجم دیسک، quota و پاک‌سازی orphan تعیین شود.
- سقف نسخهٔ فعلی ۲۰ مگابایت برای هر فایل است؛ تنظیم PHP و وب‌سرور باید با آن سازگار باشد. chunk upload پیاده نشده است.
- متن فعلی به‌صورت plain text ذخیره می‌شود تا HTML خام وارد نشود. rich-text پس از انتخاب sanitizer معتبر قابل افزودن است.
- دسترسی اختصاصی per-asset/per-folder برای user/role/group، inheritance پوشه، انتقال اتمیک درخت پوشه، اتصال گفتگو/جلسه و سیاست «همهٔ ورودی‌ها از DAM» نیازمند مراحل بعدی است.

## اجرای پیاده‌سازی در این مرحله

### هسته و API مرکزی
- کنترلر DAM تقویت شد: فهرست صفحه‌بندی‌شده با فیلتر ترکیبی (نوع، جست‌وجوی متن/عنوان/توضیح/برچسب، پروژه، وظیفه، دپارتمان، پوشه، دسته‌بندی، وضعیت، مالک و محرمانگی)، مرتب‌سازی کنترل‌شده، آمار واقعی و feed فعالیت.
- ریشهٔ بدون پوشه با `folder_id=0` فیلتر می‌شود؛ مقدار ناموجود در URL به معنای فهرست کلی باقی می‌ماند.
- عملیات گروهی انتقال و بایگانی با تراکنش دیتابیس و ثبت activity اضافه شد؛ اتصال قبلی دارایی به پروژه/وظیفه با انتقال حفظ می‌شود.
- endpoint پیش‌نمایش خصوصی برای تصویر امن، صدا، ویدیو، PDF و متن ساده ایجاد شد؛ SVG/HTML و قالب‌های دیگر inline نمی‌شوند. download/preview همچنان مجوز بک‌اند را بررسی می‌کند.
- رویدادهای تغییر پوشه، وضعیت، محرمانگی و مالکیت نام‌گذاری و با metadata ثبت می‌شوند.
- روابط `DamAsset`، `DamActivity` و مالک/پوشه/دسته‌بندی برای پاسخ API تکمیل شد. checksum در شناسنامهٔ فایل قابل نمایش است، اما مسیر و نام فیزیکی ذخیره‌سازی مخفی می‌ماند.

### رابط کاربری
- `DamMainView` اکنون به همان `DamLibrary` متصل است که در بستر پروژه و وظیفه استفاده می‌شود؛ صفحهٔ DAM دیگر از تعداد و رکوردهای نمایشی `AppContext` به‌عنوان مخزن واقعی استفاده نمی‌کند.
- صفحه با زبان طراحی تدبیر (فارسی/RTL، Vazirmatn، پنل سفید، slate/indigo/amber، جدول واکنش‌گرا و گوشه‌های گرد) بازطراحی شد.
- درگاه مشترک ثبت فایل/محتوا، ورودی چندفایلی با progress، صف مستقل خطا و retry، انتخاب پوشه در مرورگرهای پشتیبانی‌شده، ایجاد ساختار پوشهٔ نسبی، برچسب/دسته‌بندی/پوشه/وضعیت/محرمانگی و روابط سازمانی دارد.
- انتخاب دارایی موجود در صفحهٔ پروژه/وظیفه، فایل را کپی نمی‌کند و فقط رابطه را ثبت می‌کند. صفحهٔ جزئیات شناسنامه، اطلاعات فنی، پیش‌نمایش مجاز، نسخه‌ها، بازیابی، activity، تغییر وضعیت/محرمانگی، انتقال و بایگانی را دارد.
- modalهای DAM قدیمی که عملیات نمایشی را در مخزن اصلی عرضه می‌کردند از layout اصلی جدا شدند و شمارندهٔ sidebar از دارایی‌های mock حذف شد.

### بررسی و تست
- `node node_modules/typescript/bin/tsc --noEmit` — موفق.
- `node node_modules/vite/bin/vite.js build` — موفق؛ Vite هشدار bundle حجیم بالای ۵۰۰ کیلوبایت صادر کرد.
- اجرای `npm run lint/build` مستقیم در checkout به‌دلیل permission فایل‌های `node_modules/.bin` ممکن نبود؛ اجرای entrypointهای Node نتیجهٔ موفق داد.
- تست Laravel **اجرا نشد** چون PHP و Composer در محیط حاضر نیستند. تست‌های Feature برای آپلود/محتوا، محرمانگی، نسخه‌بندی/بازیابی، فیلتر ریشه، summary و انتقال گروهی موجود یا تکمیل شدند و باید در محیط PHP اجرا شوند:
  `cd backend && php artisan test --filter=DamLibraryTest`

## کارهای باقی‌مانده — تکمیل‌نشده
- مجوز اختصاصی `AssetPermissions` برای کاربر/نقش/گروه و ACL/inheritance پوشه.
- نمای سطل بازیابی‌شده در UI و عملیات restore از آن؛ endpoint بازیابی موجود است، اما تجربهٔ trash کامل نیست.
- انتقال/تغییرنام پوشه از طریق تعامل درختی، حذف پوشه و انتقال اتمیک تمام زیردرخت.
- انتخاب چند پروژه/وظیفه در یک فرم، مالک قابل انتخاب، مدیریت کامل دسته‌بندی و tag، diff متن و نمایش کامل activity در صفحات جزئیات.
- اتصال پیوست گفتگو، جلسه، دبیرخانه و تمام نقاط legacy به DAM مرکزی. **این بخش‌ها هنوز نباید ادعا کنند تمام فایل‌های سامانه را DAM مدیریت می‌کند.**
- quota، upload idempotency برای خطای مبهم شبکه، checksum verification دوره‌ای، orphan cleanup، حذف فیزیکی امن، OCR/media processing، chunk upload و آزمایش اتصال خارجی مانند MEGA.
- اجرای کامل تست‌های backend، تست مرورگر/امنیت و ارزیابی استقرار لازم است.
