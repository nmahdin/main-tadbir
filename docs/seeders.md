# سید اولیهٔ حداقلی تدبیر

## داده‌هایی که ساخته می‌شوند

اجرای `DatabaseSeeder` روی دیتابیس تازه فقط این موارد را می‌سازد:

- catalogue مجوزهای واقعی سامانه؛ هیچ مجوز وابسته به API/UI به‌عنوان دادهٔ نمونه حذف نشده است.
- نقش `admin` (مدیر اصلی سیستم) با تمام مجوزها و نقش غیرسیستمی `team_member` (کاربر) با مجوز پایهٔ `tasks.view`.
- دقیقاً سه حساب:

| نام | نام کاربری | نقش اولیه |
|---|---|---|
| مهدی نبوی | `mahdi.nabavi` | مدیر اصلی سیستم |
| عماد هندی | `emad.hendi` | کاربر |
| امیرعلی شیرازی | `amirali.shirazi` | کاربر |

دو کاربر عادی مجوز مدیریت کاربران/نقش‌ها، حذف عمومی، تأیید یا انتشار ندارند. `tasks.view` طبق قرارداد فعلی سامانه مشاهدهٔ ماژول وظایف است، نه فیلتر اجباری «فقط وظایف من». استثنای انجام کار واگذارشده همان ACL موجود بک‌اند است؛ تعیین نقش و دسترسی بیشتر بر عهدهٔ مدیر است.

سیدرهای نمونهٔ دپارتمان، پروژه، قالب پروژه و تسک حذف شده‌اند؛ وابستگی به IDهای فرضی فرانت‌اند و fallback انتساب کاربران ناشناخته به مدیر نیز حذف شده است. دپارتمان فرضی، سمت شغلی، شماره تلفن، آواتار شخص ثالث، مهارت، سابقهٔ ورود یا تأیید ایمیل ساختگی ساخته نمی‌شود. تنظیمات واقعی و workflowهای موجود پاک نمی‌شوند. داده‌های demo صریح فرانت‌اند مستقل از این سید هستند و در تولید فعال نمی‌شوند.

## رمز و ایمیل

رمز عمومی `password` و هر رمز ثابتِ داخل source حذف شده‌اند. پیش از اولین اجرای سید، در محیط امن نصب/فایل `.env` محافظت‌شده مقادیر متفاوت و قوی این متغیرها را تعیین کنید:

- `SEED_MAHDI_PASSWORD`
- `SEED_EMAD_PASSWORD`
- `SEED_AMIRALI_PASSWORD`

هر رمز حداقل ۱۲ نویسه و حداکثر ۷۲ بایت دارد (محدودیت bcrypt). مقدار واقعی را در Git، گفتگو، screenshot یا log قرار ندهید. نبود/نامعتبر بودن رمز حساب جدید، کل سید را rollback می‌کند؛ حساب نصفه ساخته نمی‌شود. password با cast موجود مدل User هش می‌شود.

چون ایمیل واقعی اشخاص اعلام نشده، پیش‌فرض‌ها از دامنهٔ رزروشده و غیرقابل‌ارسال `users.invalid` استفاده می‌کنند. این‌ها آدرس واقعی اشخاص نیستند. برای ایمیل واقعی، پیش از سید `SEED_MAHDI_EMAIL`، `SEED_EMAD_EMAIL` و `SEED_AMIRALI_EMAIL` را تنظیم کنید؛ یا پس از ورود از پنل تغییر دهید. بازیابی رمز با ایمیل تا تنظیم ایمیل واقعی و SMTP قابل اتکا نیست. ورود با نام کاربری پشتیبانی می‌شود؛ هیچ ایمیلی خودکار تأییدشده علامت نمی‌خورد.

پس از راه‌اندازی موفق، متغیرهای رمز اولیه را از محیط بردارید؛ config cache نیز با روش امن نصب باید هماهنگ شود. رمزهای ذخیره‌شدهٔ کاربران با حذف این متغیرها تغییر نمی‌کنند.

## رفع خطای «تنظیمات امن حساب … ناقص یا نامعتبر است»

این خطای نسخهٔ قبلی علت دقیق را تفکیک نمی‌کرد. نسخهٔ جدید نام متغیر مشکل‌دار و علت آن را بدون چاپ مقدار رمز/ایمیل نشان می‌دهد؛ خالی‌گذاشتن ایمیل اختیاری هم مانند تعریف‌نکردن آن، به آدرس رزروشدهٔ `users.invalid` برمی‌گردد.

1. فایل **`.env` کنار `artisan`** را ویرایش کنید؛ در این مخزن `backend/.env` است. تغییر `.env.example` یا فایل محیط فرانت‌اند کافی نیست. فایل موجود را با مثال بازنویسی نکنید.
2. برای هر سه متغیر `SEED_MAHDI_PASSWORD`، `SEED_EMAD_PASSWORD` و `SEED_AMIRALI_PASSWORD` رمز متفاوت با حداقل ۱۲ نویسه و حداکثر ۷۲ بایت بگذارید. مقادیر را با رعایت قالب dotenv داخل کوتیشن قرار دهید، مخصوصاً اگر `#` یا فاصله دارند. رمزها را در گفتگو/لاگ نفرستید. رشته‌های خالی و مقدار ویژهٔ dotenv مانند `null` رمز محسوب نمی‌شوند.
3. اگر ایمیل واقعی تعیین می‌کنید، باید معتبر و مختص همان حساب باشد. مقدار نامعتبر یا ایمیل متعلق به حساب دیگر با خطای مستقل `_EMAIL` رد می‌شود؛ به حساب قبلی دست زده نمی‌شود.
4. در ترمینال محلی و پوشه‌ای که `artisan` دارد اجرا کنید:

```bash
php artisan config:clear
php artisan db:seed
```

`config:clear` برای خواندن مقادیر تازهٔ `.env` به‌جای config cache قدیمی است. نیازی به `migrate:fresh`، حذف دیتابیس، ساخت دوبارهٔ جداول یا تغییر `APP_KEY` نیست. رمز عمومی/ثابت برای عبور از این خطا اضافه نشده و اعتبارسنجی امنیتی همچنان برقرار است. این دستورات برای محیط محلی دارای CLI هستند؛ محدودیت هاست بدون SSH به قوت خود باقی است.

## اجرای امن و تکرارپذیر

روی دستگاه توسعه/CI با PHP سازگار و کپی دیتابیس (نه هاست فاقد SSH):

```bash
# پس از تنظیم امن محیط و گرفتن backup
php artisan migrate
php artisan db:seed
```

- `migrate:fresh` برای دیتابیس دارای اطلاعات توصیه یا اجرا نمی‌شود.
- اجرای دوباره، حساب موجود با همان username را تغییر نمی‌دهد: نام، رمز، ایمیل، نقش، وضعیت، اطلاعات تماس و تاریخچه حفظ می‌شوند. حساب‌های دیگر، از جمله حساب‌های ساخته‌شده با سیدر قبلی، **خودکار حذف، تغییرنام یا تبدیل به مدیر نمی‌شوند**.
- برخورد ایمیل با حسابی دیگر خطا می‌دهد؛ حساب موجود تصاحب نمی‌شود.
- نقش عادی موجود و مجوزهای ویرایش‌شدهٔ آن حفظ می‌شوند؛ نقش غیرفعال دوباره فعال نمی‌شود. نقش مدیر مطابق قرارداد سیستمی تمام مجوزهای catalogue را دریافت می‌کند.
- وجود حساب/نقش قدیمی با مشخصات متفاوت نیازمند بررسی صریح مدیر است؛ این سید ابزار پاک‌سازی دادهٔ زنده نیست.
- ساخت سه حساب جدید به یک تراکنش محدود است؛ مجوز، نقش و کاربران در DatabaseSeeder نیز در تراکنش واحد قرار دارند.
- برای هاست بدون SSH/Cron، آماده‌سازی و آزمون روی کپی DB و انتقال امن با ابزار کنترل‌پنل طبق [deployment.md](deployment.md) انجام شود. endpoint عمومی اجرای seed/migration ساخته نشده است؛ APP_KEY موجود را تغییر ندهید.

این تغییر فقط source سیدر و بستهٔ انتشار را به‌روزرسانی می‌کند؛ اجرای سید روی دیتابیس تولید یا حذف کاربران نصب موجود انجام نشده است.

## آزمون

`InitialSeedTest`: شش سناریو و ۷۹ assertion برای سه حساب دقیق و حداقل دسترسی، نبود دادهٔ نمونه، حفظ حساب/نقش/پروژه پس از reseed، rollback رمز نامعتبر، جلوگیری از تصاحب ایمیل، عدم فعال‌سازی مجدد نقش غیرفعال و ورود و کنترل دسترسی واقعی API. تست‌ها روی SQLite ایزوله با PHP-WASM اجرا شده‌اند؛ تأیید هاست و MySQL نیستند.

رگرسیون کامل همین نوبت: **۲۵۶ تست / ۱۴۹۰ assertion بک‌اند موفق**، **۳۴ تست Node موفق**، TypeScript و build تولید موفق. هشدار اندازهٔ chunk همچنان برقرار است. آزمون‌های مرورگر نوبت قبلی در گزارش فازها ثبت شده‌اند و جای آزمون دوبارهٔ هاست واقعی را نمی‌گیرند.

### آزمون اصلاح پیام تنظیمات اولیه

پس از تفکیک خطاها و پشتیبانی از ایمیل اختیاری خالی: `InitialSeedTest` با **۹ تست / ۱۰۲ assertion** و کل suite با **۲۵۹ تست / ۱۵۱۳ assertion** موفق شد (PHP-WASM / SQLite). پوشش جدید شامل متغیر دقیق خطا، عدم افشای مقدار، fallback ایمیل خالی و مرز ۷۲ بایت برای رمز چندبایتی است. فرانت‌اند و artifact این اصلاح تغییر نکرده‌اند.
